Для R03 проверено требование: после успешного CONNECT данные за заголовком
принадлежат целевому серверу, а успехом считается любой `2xx`.
Источник: [RFC 9110, §9.3.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.6).
В TCP-пути используется `peek` с последующим чтением ровно заголовка. В TLS-пути
общий парсер ограничивает каждое чтение остатком разделителя; расшифрованные
данные сохраняются внутренним буфером TLS. Публичные возвращаемые типы сохранены.

Вместе с исправлениями уменьшены конкретные расходы:

| Участок | Было | Стало |
|---|---|---|
| Проверка пользователя | Поиск `O(U)` и клонирование PHC-строки даже при попадании в кэш | Поиск в неизменяемом `HashMap`, ожидаемое `O(1)`; попадание в кэш обходится без PHC-копии и очереди хэширования |
| Двусторонний туннель | Два `tokio::io::split`: две аллокации `Arc`, `Mutex` вокруг обоих потоков | Копирование без `split`; учёт активности без дополнительных heap-объектов; два буфера по 16 КиБ сохранены |
| Поиск конца HTTP-заголовка | При чтении по одному байту суммарное сканирование `O(H²)` | Сканирование `O(H)` с перекрытием в три байта |
| SOCKS5/HTTP, обычный/recovery-путь | Четыре варианта подготовки и запуска передачи | Общая функция с едиными ограничениями времени |

`U` — число пользователей, `H` — размер заголовка. Это изменения структуры
расходов, подтверждённые кодом. Численного выигрыша по CPU, RSS, throughput
или p95/p99 без измерений этот отчёт не заявляет.

**R11 — P1 — Неограниченный sticky-кэш.**
[ProxyRotator::link_proxy:73](../crates/resocks5-net/src/rotator/mod.rs#L73).
Каждый успешно достигнутый новый `target_addr` остаётся в `DashMap`. Удаление
происходит только при последующей неудаче именно этого адреса; TTL и ограничение
числа записей отсутствуют. Последовательность уникальных доступных назначений
даёт рост памяти `O(T)` за время работы, несмотря на лимит одновременных клиентов.
Нужен ограниченный кэш с политикой вытеснения и сроком жизни. Проверка исправления:
много последовательных разных адресов при небольшом лимите, включая параллельные
вставки; число записей всегда остаётся в заданной границе.

**R12 — P1 — Неатомарная запись пользователей.**
[Init-claim:223](../crates/resocks5/src/auth/state.rs#L223),
[CLI:196](../crates/resocks5/src/cli/run_user_command.rs#L196).
Проверен разрешённый исходник `ktav 0.6.1`: `to_file` вызывает `fs::write`.
Существующий файл сначала обрезается; ошибка записи или остановка процесса может
оставить неполный файл. Возврат `hash = "init"` восстанавливает только память.
Тест ошибки несуществующего каталога не проверяет отказ после обрезания файла.
Нужна запись во временный файл в том же каталоге с последующей атомарной заменой
и явно выбранной гарантией сохранности при сбое. Проверять отказ записи после
частичного вывода и сохранность предыдущего файла.

**R13 — P1 — Init-claim затирает более поздние изменения CLI.**
[state.rs:188](../crates/resocks5/src/auth/state.rs#L188),
[снимок для записи:216](../crates/resocks5/src/auth/state.rs#L216).
Сценарий не требует одновременных системных вызовов: сервер запускается;
CLI добавляет/отключает пользователя; затем другой пользователь с `hash = "init"`
входит впервые. Сервер перезаписывает весь файл своим старым снимком. Добавленный
пользователь исчезает, отключение или новый пароль могут быть отменены на диске.
Внутрипроцессный `RwLock` не согласует сервер с CLI. Нужен единый владелец записи
либо межпроцессная синхронизация с чтением актуального состояния и слиянием одной
операции. Одна атомарная замена из R12 не устраняет потерю обновлений.

**R14 — P1 — Цепочка через gate не учитывает лимит конечного upstream.**
[use_gate:41](../crates/resocks5/src/server/establish_connection.rs#L41).
Permit берётся только у gate; второе SOCKS5-соединение внутри него не резервирует
слот у `proxy_config`. Прямые и проходящие через разные gates соединения к одному
upstream обходят общий `max_per_upstream`. Нужен учёт каждого узла цепочки и
удержание всех соответствующих permits до конца туннеля. Проверять совместную
нагрузку прямого и цепочного путей и освобождение обоих permits при отказе любой
стадии; не исправлять простым увеличением лимита.

**R15 — P2 — Gate-путь всегда использует SOCKS5.**
[use_gate:41](../crates/resocks5/src/server/establish_connection.rs#L41),
[сбор списков:67](../crates/resocks5/src/main.rs#L67).
В rotator попадают HTTP/HTTPS-конфигурации, но обе стадии `use_gate` вызывают
`handshake_over_stream` без выбора транспорта. HTTP-gate или HTTP/HTTPS-второй
прокси получает SOCKS5-байты. Нужен выбор handshake по протоколу каждого узла,
включая вложенный TLS, либо явный отказ от неподдерживаемой комбинации при загрузке
конфига. Проверять матрицу сочетаний, а не только SOCKS5 → SOCKS5.

**R16 — P2 — Жизненный цикл refill-задач и учёт запасных сокетов.**
[proxy_pool.rs:315](../crates/resocks5-net/src/pool/proxy_pool.rs#L315).
Refill-задача отсоединяется и удерживает `Arc<ProxySpares>` бесконечно: уничтожение
`ProxyPool` в продолжающем работать runtime её не останавливает. Проверка
`contains_key` и последующий `insert` также неатомарны: два вызова могут запустить
две задачи, одна из которых заполняет уже недоступную через карту очередь.
Кроме того, запасные `PreWarmed`-сокеты открываются без permits и не входят в
заявленный лимит TCP-соединений. Нужны атомарное создание записи, управляемое
завершение задач и единая модель учёта активных/запасных соединений. В просмотренной
рабочей конфигурации прогрев выключен; это не причина её текущих ошибок.

**R17 — P2 — IPv6 не проходит через все границы протоколов.**
[parse_proxy_str.rs:24](../crates/resocks5-net/src/connect/parse_proxy_str.rs#L24),
[handshake_over_stream.rs:62](../crates/resocks5-net/src/connect/handshake_over_stream.rs#L62),
[SOCKS5 ATYP=4:465](../crates/resocks5/src/server/handle_socks5_client.rs#L465).
`split(':').collect()` отвергает IPv6-литерал в списке upstream. Входящий HTTP-target
`[::1]:443` при передаче через SOCKS5 становится доменом `[::1]`, а SOCKS5-target IPv6
форматируется без скобок для последующего HTTP CONNECT. Нужен единый тип адреса,
разделение разбора host/port и отображения HTTP authority; заодно убрать временные
`Vec<&str>` и корректно обработать двоеточие в пароле. Проверять IPv4, домен и IPv6
во всех сочетаниях входного и выходного протоколов.
Требование отдельного ATYP IPv6: [RFC 1928, §5](https://www.rfc-editor.org/rfc/rfc1928.html#section-5).

**R18 — P2 — Бюджет попыток расходуется на повторения и может не оставить прямого fallback.**
[Кэш:134](../crates/resocks5/src/server/establish_connection.rs#L134),
[gates:202](../crates/resocks5/src/server/establish_connection.rs#L202),
[прямой путь:263](../crates/resocks5/src/server/establish_connection.rs#L263).
Неудачный cached upstream может сразу снова появиться в `pick_order`. При бюджете
две попытки это способно исключить ещё не проверенный здоровый upstream. Полный
перебор `gates × proxies` может аналогично исчерпать бюджет до прямого пути.
Нужно учитывать уже проверенные маршруты и распределять бюджет между вариантами
доступа. Проверять небольшой бюджет с мёртвым кэшем/gate и доступным fallback.

**R19 — P2 — Реальный отказ одной стадии штрафует оба узла цепочки.**
[establish_connection.rs:252](../crates/resocks5/src/server/establish_connection.rs#L252).
Отказ TCP до gate снижает рейтинг и конечного прокси, которого вообще не достигли;
отказ конечного сервера также штрафует gate. R07 исключает только ошибочную
обработку `AtCapacity`. Для остальных ошибок нужна классификация стадии и
разделение отказа транспорта, авторизации и назначения, чтобы не переносить
неисправность одного узла на рейтинг остальных.

**R20 — P2 — Рейтинг разных конфигураций с одним endpoint смешивается.**
[Создание индекса:55](../crates/resocks5-net/src/rotator/mod.rs#L55),
[index_of:112](../crates/resocks5-net/src/rotator/mod.rs#L112).
Ключ `(host, port)` не учитывает протокол и учётную запись. Более поздняя запись
заменяет индекс предыдущей, хотя обе остаются в `proxies`: отказ одной меняет
рейтинг другой. Нужна стабильная идентичность конфигурации, сохраняющаяся при
создании cached-конфигурации с gate. Проверять два разных аккаунта и два протокола
на одном endpoint с независимыми исходами.

**R21 — P2 — Восстановление имени и фрагментация зависят от границ TCP-чтения.**
[SOCKS5 recovery:245](../crates/resocks5/src/server/handle_socks5_client.rs#L245),
[HTTP recovery:285](../crates/resocks5/src/http_proxy/handle_http_client.rs#L285),
[подготовка пакета:40](../crates/resocks5/src/server/forward_tunnel.rs#L40).
Одно чтение до 16 КиБ не гарантирует целый ClientHello или строку Host. Например,
первые пять байтов TLS отдельно дают отсутствие SNI и не проходят шестибайтовую
сигнатуру фрагментации; оставшаяся часть идёт обычной передачей. Нужны ограниченный
сбор префикса/записи и тесты всех разбиений. Отдельное ограничение recovery:
при IPv4-литерале сервер отвечает успехом до подключения upstream и ждёт полезную
нагрузку. SSH/SMTP, ожидающие приветствие сервера, на этом пути по-прежнему
заканчиваются таймаутом. Нужно ограничить применение recovery совместимыми
сценариями или спроектировать явный fallback. R02 исправляет обычный путь, но
не меняет этот выбор маршрута.

**R22 — P2 — Численная устойчивость выбора и валидация настроек.**
[select.rs:28](../crates/resocks5-net/src/rating/select.rs#L28),
[policy.rs:37](../crates/resocks5-net/src/rating/policy.rs#L37).
При малых допустимых весах `u.powf(1 / w)` обнуляется: для `w = 1e-6` и
`u = 0.25` или `0.75` результат `f64` равен нулю. Стабильная сортировка равных
ключей сохраняет исходный порядок и нарушает равномерность при равных весах.
Сравнение логарифмических ключей устраняет этот механизм. Также нет общей
проверки конечности и диапазонов `half_life`, `sand_max`, `min_weight`,
`success_factor`; например, `sand_max = 0` даёт неопределённый вес свежей ячейки.
Проверять крайние валидные веса и отклонение невалидной конфигурации при старте.

**R23 — P2 — Некоторые неработоспособные конфигурации принимаются молча.**
[parse_list:67](../crates/resocks5/src/main.rs#L67),
[проверка пустого пула:155](../crates/resocks5/src/main.rs#L155).
`filter_map` без диагностики выбрасывает ошибочную строку upstream. Наличие только
gates проходит проверку непустого пула, хотя ни одного конечного upstream нет и
обычный клиент получает `All 0 upstream attempts ... failed`. Нужна проверка
наличия доступного маршрута с учётом direct-пользователей и диагностирование
ошибочных строк без раскрытия их credentials. В предоставленном конфиге также
остались `cb_*` поля, отсутствующие в текущем `NetworkConfig`; старые настройки
не следует считать действующими настройками нового бинарника.

зависимостей требует отдельного разрешения. Предупреждения не подавлялись.

**R25 — P2 — Завершение и ошибки фоновых задач недостаточно наблюдаемы.**
[Логгер:190](../crates/resocks5/src/main.rs#L190),
[JoinSet:99](../crates/resocks5/src/server/run_server.rs#L99).
Задача логгера не ожидается при завершении; сообщения, включая завершающие,
могут остаться в очереди. Ошибки записи/flush файла игнорируются. Ошибки завершения
обработчиков из `JoinSet` тоже отбрасываются, включая `JoinError` после panic.
Нужны закрытие канала с ограниченным drain логгера, обработка ошибок приёма
результатов задач и явная реакция на отказ файлового вывода. Проверять queued-лог
при штатном shutdown и отказ назначения вывода.

**R26 — P3 — Полная сортировка и аллокации внутри общего Mutex рейтингов.**
[Ratings::pick_order:114](../crates/resocks5-net/src/rating/mod.rs#L114),
[weighted_order:28](../crates/resocks5-net/src/rating/select.rs#L28).
Под блокировкой строится вектор весов, создаются ключи и выполняется полная
сортировка `O(N log N)`, хотя бюджет попыток обычно использует лишь префикс.
Это подтверждённый участок сериализации, но его вклад в задержки не измерен.
Направление оптимизации: краткий снимок состояния, генерация/сортировка вне
блокировки, выбор только нужного числа кандидатов с сохранением распределения.
До смены алгоритма нужны измерения для разных размеров пула и проверки
вероятностных свойств с фиксированным seed.

**R27 — P3 — Лишняя работа на пути попытки и записи логов.**
[index_of:112](../crates/resocks5-net/src/rotator/mod.rs#L112),
[acquire:244](../crates/resocks5-net/src/pool/proxy_pool.rs#L244),
[Logger:26](../crates/resocks5/src/logger/log.rs#L26),
[flush:224](../crates/resocks5/src/main.rs#L224).
Неизменяемый reverse-index использует `DashMap`, а поиск клонирует host.
Получение соединения дополнительно форматирует endpoint. Логгер форматирует
сообщение до отказа `try_send` при полной очереди; файловый `BufWriter` сбрасывается
после каждой строки. Кандидаты: неизменяемый индекс с заимствованным поиском,
ленивая подготовка диагностических строк, резервирование места до форматирования,
сброс пачками/по таймеру с заданной гарантией shutdown. Изменять после измерения
частоты и стоимости соответствующих операций, сохраняя выбранную политику потери логов.

**R28 — P3 — Документация местами обещает другое поведение.**
[README](../README.md), [SmallRng::from_os](../crates/resocks5-net/src/rating/rng.rs#L15).
В README одновременно упоминаются round-robin и взвешенный случайный выбор;
равные веса дают равномерный случайный выбор, а не циклическое обслуживание.
`from_os` использует время и идентификатор потока, несмотря на описание OS entropy.
Утверждение об отсутствии потребности в C toolchain для `ring` также неверно:
сборка включает C/assembler-компоненты, описанные в
[инструкции сборки ring](https://github.com/briansmith/ring/blob/main/BUILDING.md).
Обновить обещания и имена по реальному
поведению. Комментарий об автоматической смене пароля в работающем процессе уже
исправлен: пользовательские настройки являются снимком и требуют перезапуска.

Логи дают следующий контекст. Проанализированный срез `resocks5.log` содержит
180 881 строку, от `2026-06-18 14:30:57` до `2026-09-08 08:55:18` по времени
самого лога. Файл продолжал пополняться, поэтому это зафиксированный срез,
а не обещание совпадения счётчиков с последующим чтением.

| Строки `All ... upstream attempts ... failed` | 9 802 |

В логе встречаются старые сообщения о circuit breaker/quarantine. Их нельзя
автоматически приписывать текущему sand-rating-коду. Число ошибок также нельзя
превратить в процент неуспешных запросов: полного знаменателя успешных запросов
в этом срезе нет. `10053` без стадии, адреса клиента и корреляции с запросом не
устанавливает причину обрыва. Сами логи не доказывают, что R01/R02 вызвали именно
эти ошибки; их механизмы подтверждены отдельными тестами. Частые capacity-отказы
делают проверку времени удержания permits и правильной классификации отказов
приоритетнее косметических оптимизаций. Сырые credentials, адреса upstream и
локальные пути в отчёт не включены.

Дополнительно выполнен Clippy с `pedantic`, проверками удержания lock через await,
unsafe, unwrap, лишних clone и арифметики. Его расширенные предупреждения

Это не заменяет проверку жизненного цикла, которую исходные зелёные тесты не покрывали.

Таймерные регрессии используют виртуальное время. Есть проверка остановленной
записи и shutdown, сохранности баннера на реальном loopback TCP, чтения заголовка
по одному байту, лимита HTTP-заголовков, отсутствия токена в ошибке и допуска
фонового хэширования. Параметры Argon2 и публичные сигнатуры сетевой библиотеки
сохранены. Полное TLS-взаимодействие с сертификатами, Linux/macOS, MSRV `1.88`,
профилирование CPU/heap и проверка всех транзитивных путей зависимостей остаются
за границами этого прохода. Собственных блоков `unsafe` в просмотренных crate нет.

цепочки и пул к единому учёту ресурсов (R14–R16), отдельно согласовать обновление

проверки; они не считаются исправленными данным коммитом.
