**R6-01 — P2 — Повторная проверка init находится до claim mutex.**

В [try_claim_init](../crates/resocks5/src/auth/state.rs#L228) hash проверяется
под коротким read guard, затем строится снимок, и только после этого берётся
[claim_lock](../crates/resocks5/src/auth/state.rs#L258). После ожидания mutex
проверка `users[idx].hash != INIT_HASH` больше не повторяется. При
[ClaimPersist::Failed](../crates/resocks5/src/auth/state.rs#L293) hash безусловно
заменяется на `"init"`, хотя этот вызов перед persistence вообще не публиковал
свой временный hash.

Допустимое чередование для двух входов с одним правильным паролем:

1. Оба входа проходят проверку `init` до mutex и первоначально не находят пароль в cache.
2. Первый сохраняет hash, публикует его в памяти и cache, возвращает успех.
3. Второй получает mutex и всё равно идёт в persistence. Например, другой процесс
   к этому моменту удерживает users-lock дольше его десятисекундного лимита.
4. Второй получает `Failed`, возвращает отказ и сбрасывает hash первого в `init`.

Так корректный пароль получает отказ вместо проверки против уже известного
победителя, а память расходится с сохранённым hash и существующей записью cache.
Проверка cache в начале `verify` не помогает уже прошедшему её конкурентному
вызову. Прежняя реализация повторно проверяла hash после захвата общей write
блокировки и не входила в persistence после завершившегося claim.

Повторять проверку состояния после получения `claim_lock`. Ошибка сохранения
не должна откатывать состояние, которого текущая попытка не меняла, или
стирать результат другого завершившегося входа. Сохранить короткие guards
`users`, не возвращая файловое I/O под RwLock. Критерий исправления: после
успешного первого claim ошибочная поздняя попытка оставляет его hash и cache
согласованными; вход с тем же паролем проверяется по победившему hash.
Это регрессия переработки R5-10, а не доказательство захвата чужого аккаунта.

**R6-02 — P2 — Idle ограничивает целый write_all внутри chunk, а не отсутствие прогресса.**

[write_progress_bounded](../crates/resocks5-net/src/connect/tls_fragment.rs#L155)
оборачивает `write_all(buf)` вместе с `flush()` в один `timeout(idle, ...)`.
Перенос таймера внутрь цикла исправляет длинную отправку множества мгновенно
записываемых chunks, но не случай частичных записей одного chunk. Успешные
частичные `write` внутри `write_all` не перезапускают этот таймер.

Расчётный сценарий: chunk 64 байта, idle 1 с, writer под обратным давлением
принимает по 8 байтов каждые 200 мс. Между успешными записями нет секундного
простоя, однако весь chunk требует больше секунды и helper возвращает
`Stalled`. [forward_tunnel](../crates/resocks5/src/server/forward_tunnel.rs#L65)
после этого закрывает потоки. Сценарий требует частичных write; мгновенно
записываемые однобайтные chunks из нового теста его не покрывают.

Есть и обратное расхождение с
[настройкой idle](../crates/resocks5/src/config/network_config.rs#L86):
`delay_ms` ожидается [вне таймера](../crates/resocks5-net/src/connect/tls_fragment.rs#L141),
поэтому даже пауза длиннее idle не считается простоем. Новая документация
helper объявляет такое исключение, а описание пользовательской настройки его не содержит.

Отсчитывать idle от последнего наблюдаемого прогресса, включая частичные
записи; при необходимости выделить отдельный предел длительности chunk/flush.
Семантику намеренных пауз согласовать с описанием настройки. Сохранить запрет
повторной отправки уже принятого префикса. Критерий исправления: длительная
запись с регулярным частичным прогрессом завершается успешно, остановившаяся
запись закрывается по idle. Общий lifetime в этом сценарии отключён либо достаточно велик.

**R6-03 — P2 — timeout(Duration::ZERO, operation) сначала запускает operation.**

[remaining_client_budget](../crates/resocks5/src/server/handle_client.rs#L19)
возвращает ноль после истечения срока. Комментарий и NetworkConfig обещают,
что следующая фаза немедленно завершится таймаутом. Однако обработчики просто
оборачивают фазу в `timeout` с этим нулём:
[SOCKS5](../crates/resocks5/src/server/handle_socks5_client.rs#L47),
[HTTP](../crates/resocks5/src/http_proxy/handle_http_client.rs#L95).

В Tokio 1.43.1 `time/timeout.rs::Timeout::poll` сначала вызывает `value.poll`,
возвращает `Ok` при `Ready` и только при `Pending` опрашивает таймер. Поэтому
готовая операция разрешена даже при нулевой длительности. Это также прямо
описано в [документации timeout](https://docs.rs/tokio/latest/tokio/time/fn.timeout.html).

Фаза с уже буферизованным запросом может успешно закончиться после своего
deadline. Даже если она вернёт `Pending`, её первый poll уже может выполнить
побочные действия: прочитать данные, ответить клиенту или вызвать
[verify_async](../crates/resocks5/src/auth/state.rs#L140), который допускает
работу в `spawn_blocking`. Последующая отмена ожидания не отменит начатый claim.
Это отдельный случай от допустимого завершения ранее допущенной проверки
после отмены: здесь новую фазу запускают уже с истёкшим сроком.

Явно отвергать истёкший deadline до входа в фазу и допуска работы. Для
неистёкшего срока использовать общий абсолютный deadline; один переход на
`timeout_at` сам по себе не меняет порядок первого poll. Критерий исправления:
готовая операция с истёкшим сроком не запускается и не производит побочных
действий. [Новый тест](../crates/resocks5/src/server/handle_client.rs#L369)
проверяет только `pending()`, поэтому не различает эти два поведения.

**R6-04 — P2 — HostPort проверяет разбиение адреса, но не допустимость байтов HTTP target.**

Входной [parse_http_connect](../crates/resocks5/src/http_proxy/handle_http_client.rs#L496)
теперь вызывает `HostPort::parse`, что устраняет прежние неверные порты.
Но [HostPort](../crates/resocks5-net/src/connect/host_port.rs#L45) для доменного
host проверяет только непустоту и отсутствие неподдерживаемого двоеточия.
Управляющие байты он не отвергает; `from_utf8` request line тоже принимает NUL.

Например, байтовая строка запроса
`CONNECT exa\x00mple.com:443 HTTP/1.1\r\n\r\n` проходит входной разбор
(здесь `\x00` обозначает один NUL). После разрешённого anonymous или успешной
аутентификации обычный маршрут вызывает
[pool.acquire](../crates/resocks5-net/src/connect/connect_http_proxy.rs#L25).
Лишь затем [write_connect_request](../crates/resocks5-net/src/connect/connect_http_proxy.rs#L92)
классифицирует этот target как недопустимый и возвращает ошибку.
[establish_connection](../crates/resocks5/src/server/establish_connection.rs#L655)
записывает её как failure исправного HTTP-upstream и продолжает попытки.

Клиентская ошибка опять расходует подключения и портит рейтинг, хотя могла
быть отвергнута до dial. Условие можно показать на одном HTTP-upstream без
каких-либо ошибок с его стороны; сетевое воспроизведение здесь не выполнялось.
Запретить недопустимые управляющие байты/разделители в target на входе, сохраняя
полезную отдельную роль HostPort как парсера пар адреса и порта. Критерий:
ответ 400, отсутствие acquire/попыток и неизменные рейтинги для такого запроса.

**R6-05 — P3 — Редкий fallback заставляет каждый claim копировать весь список пользователей.**

В [try_claim_init](../crates/resocks5/src/auth/state.rs#L247) до получения
`claim_lock` безусловно клонируется весь `Vec<User>`, включая принадлежащие
пользователям строки name/hash. Этот снимок нужен только ветке
[отсутствующего файла](../crates/resocks5/src/auth/state.rs#L331), где затем
выполняется ещё один `fallback_users.to_vec()`.

В обычном случае users-файл существует: persistence читает и изменяет его,
а подготовленный полный снимок выбрасывается. Для U пользователей добавлены
лишние `O(U)` работа и глубокое копирование строк на каждую попытку claim,
включая будущих проигравших гонку. Копирование выполняется под read guard,
удлиняя задержку публикации изменений, которым нужен write guard.

Готовить fallback только при фактической необходимости, после сериализации
claim и повторной проверки состояния. При передаче владения снимком избежать
второго глубокого клонирования. Сохранить согласованность первоначального
создания файла и слияния текущего состояния на диске. Критерий: обычный claim
при существующем файле не копирует in-memory список целиком ради fallback.
Общая асимптотика чтения/перезаписи users-файла от этого сама по себе не изменится.

**R6-06 — P3 — Разбор HTTP по байтам не требует вектора всех строк.**

[Новый парсер](../crates/resocks5/src/http_proxy/handle_http_client.rs#L461)
сначала накапливает `Vec<&[u8]>` для всех строк, затем разбирает первую строку
и один раз ищет Proxy-Authorization. Раньше строки перечислялись итератором
без отдельной таблицы. Исправление obs-text требует разбора по байтам, но
не требует материализации всех срезов.

В пределах установленного лимита 16 КиБ помещается около 4000 коротких
заголовков вида `X:\r\n`. Одни элементы таблицы срезов занимают около 64 КиБ
на 64-разрядной платформе, дополнительно к исходному буферу; вектор ещё и
растёт по мере разбора. Расход ограничен лимитом заголовков, но эта новая
аллокация находится на пути каждого CONNECT и не нужна дальнейшему алгоритму.

Перечислять CRLF-строки ленивым итератором по байтам или разбирать их одним
проходом без отдельной коллекции. Сохранить разделение заголовков и pipelined
payload, лимит размера и поддержку opaque-значений. Критерий: нет таблицы
срезов пропорционально числу заголовков; результат разбора прежних допустимых
запросов и обработка ошибок сохраняются. Значение экономии для обычного
небольшого запроса не измерялось.

**R6-07 — P3 — Задержки в новых тестах не подтверждают наступление нужной фазы.**

[anchor_first_poll](../crates/resocks5/src/server/handle_client.rs#L175)
выполняет 50 `yield_now` с реальными `thread::sleep(1 ms)`. Затем deadline-тесты
соединяют paused Tokio clock с реальным TCP и предполагают, что данные
перевели обработчик именно в handshake/recovery до следующего срабатывания
виртуального таймера. Helper не получает подтверждения этих переходов.
Paused clock автоматически продвигается к следующему таймеру, когда runtime
не находит готовой работы; доставка TCP от виртуального времени не зависит.
Это поведение есть в Tokio 1.43.1 и описано в
[документации pause](https://docs.rs/tokio/latest/tokio/time/fn.pause.html#auto-advance).

В [тесте users-lock](../crates/resocks5/src/auth/state.rs#L1030) подтверждается
захват файлового lock, но вход T1 в persistence заменён
[sleep(300 ms)](../crates/resocks5/src/auth/state.rs#L1053). Lock отпускается
по трёхсекундному таймеру, а результат другого входа оценивается по 1500 мс
реального времени. Если T1 ещё не дошёл до своей критической секции, старый
код может пройти проверку: Alice и проверка sentinel успеют завершиться
до блокировки T1. Иное планирование может также нарушить временные assertions
без регрессии производственного кода.

Это статически обнаруженная зависимость от планирования, а не наблюдение
флейка в этом раунде. Синхронизировать тесты событиями входа в нужную фазу,
удерживать файловый lock до явного разрешения освободить его. Для виртуальных
deadline отделить проверяемый таймер от неконтролируемой доставки TCP либо
управлять переходами через подтверждения. Критерий: тест действительно
застал требуемое конкурентное состояние, а его исход не определяется числом
sleep/yield и скоростью Argon2 на конкретной машине.

**R6-08 — P3 — Тест запрета лишних построений проверяет только количество попыток.**

[budget_exhausted_by_cache_failure_makes_no_further_attempts](../crates/resocks5/src/server/establish_connection.rs#L1255)
проверяет текст `All 1 upstream attempts` и отсутствие новой sticky-привязки.
Оба свойства уже обеспечивал код до `f6019c9`: внутренние проверки бюджета
запрещали дальнейший dial, но порядок gates/proxies строился до этих проверок.

Если вернуть только прежнее расположение построений `pick_order`, оставив
старые внутренние guards, проверяемые значения не изменятся. Следовательно,
тест не защищает именно оптимизацию R5-09, ради которой добавлен. Это вывод
из сравнения веток до и после изменения; мутация и тест не запускались.

Наблюдать число построений порядка или число сгенерированных ключей, а не
только число сетевых попыток. Критерий: возврат лишнего `pick_order` после
исчерпания бюджета обнаруживается проверкой, даже когда ни одного лишнего
соединения не открыто. Саму полезную проверку верхней границы попыток можно сохранить.

**R6-09 — P3 — Тест ограниченного teardown не вызывает production-wrapper.**

[runtime_teardown_is_bounded_with_a_stuck_blocking_write](../crates/resocks5/src/main.rs#L764)
создаёт собственный runtime, запускает parked blocking-операцию и напрямую
вызывает `runtime.shutdown_timeout(500 ms)`. Производственная функция
[run_server](../crates/resocks5/src/main.rs#L173), её catch_unwind и её выбор
способа завершения runtime тестом не вызываются.

Возврат production-кода к неограниченному `Runtime::drop` не меняет ни одной
исполняемой этим тестом операции. Поэтому проверяется поведение отдельного
Tokio runtime, а не защита приложения от исходного R5-06. Дополнительно нет
подтверждения, что blocking-операция действительно начала исполняться до
shutdown: queued-задача может быть отменена до старта. Если она стартовала,
бесконечный park не имеет пути освобождения до конца тестового процесса.

Проверять общий с production код владения/завершения runtime или остановку
реального дочернего приложения с управляемым назначением вывода. Подтверждать
начало блокирующей операции и предусмотреть её освобождение при завершении
проверки. Критерий: возврат неограниченного teardown именно в приложении
обнаруживается, а сценарий достоверно содержит начавшееся зависшее I/O.
Само исправление production-пути по чтению кода присутствует; этот пункт о
недостаточной защите от его регрессии.

**Повторная оценка раунда 5.**

Статус ниже основан на чтении изменений. Он не означает повторного прогона
старых или новых проверок.

| Прежний пункт | Состояние на базе раунда 6 |
|---|---|
| R5-01, неверный порт CONNECT | Порты проверяются до dial. Валидация других байтов target остаётся неполной: R6-04. |
| R5-02, новый бюджет на каждой фазе | Фазы используют остаток общего deadline. Отсутствует явный запрет входа в фазу после его истечения: R6-03. |
| R5-03, таймер всей отправки ClientHello | Исправлен сценарий длинной последовательности быстро записываемых chunks. Частичный прогресс одного chunk и семантика пауз остаются: R6-02. |
| R5-04, закрытый spare | Добавлен неблокирующий probe EOF/ошибки/неожиданных данных с переходом к fresh connect. Остаточная гонка после probe явно описана в коде. |
| R5-05, SIGTERM | Unix SIGTERM зарегистрирован и ведёт в общий drain. Согласование внешнего срока остановки контейнера с 30 с drain и последующим завершением логгера/runtime в документации развёртывания ещё не отражено. |
| R5-06, неограниченный runtime teardown | Runtime явно принадлежит wrapper и завершается через shutdown_timeout; завершающая диагностика использует ограниченное async-ожидание. Ограничение теста этой защиты — R6-09. |
| R5-07, нулевой пароль | Нулевые ULEN/PLEN отвергаются в SOCKS5; пустой пароль отдельно запрещён в общем try_claim_init. |
| R5-08, obs-text | Неиспользуемые поля разбираются по байтам. Новая лишняя таблица строк — R6-06. |
| R5-09, полный порядок при малом бюджете | Проверки бюджета перенесены перед построениями. Полные O(N log N) сортировки для ещё не исчерпанного малого бюджета и повторные порядки для gates остаются; эта часть P3 не закрыта. |
| R5-10, users RwLock на протяжении persistence | Файловое I/O вынесено из users RwLock. Появились гонка повторной проверки и лишний снимок: R6-01, R6-05. |
| R5-11, endpoint и IPv6 | Диагностическая строка готовится при ошибке, acquire/refill передают host и port кортежем. Описанные лишние операции устранены. |
| R5-12, переполнение суммы весов | Суммируются нормированные конечные положительные веса; прежний случай с двумя f64::MAX устранён. |

Рекомендуемый порядок: восстановить корректность claim и границы клиентского
ввода/таймаутов (R6-01–R6-04), затем убрать новые лишние копии (R6-05, R6-06)
и сделать проверки чувствительными к соответствующим регрессиям (R6-07–R6-09).
Для оставшегося R5-09 выбирать ограниченный префикс с сохранением распределения
следует отдельно, после оценки размеров реальных списков прокси.
