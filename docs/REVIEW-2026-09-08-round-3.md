R3-01 связан с документированными результатами ReplaceFileW: при коде 1176
без backup старый файл может уже отсутствовать, а replacement остаётся под
временным именем; при 1177 replacement также сохраняется. Сам частичный отказ
ОС не инъецировался: тест воспроизводит состояние оставшейся копии перед
следующей записью. [Документация ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew).

Сохранение `.tmp` намеренно блокирует следующую запись до разбора этой копии.
Автоматическое удаление или выбор версии для восстановления здесь не добавлены.
Это относится и к обычному падению между созданием временного файла и commit.

R3-02 согласован с контрактом Tokio: отмена `write_all` не откатывает уже
отправленный префикс, а повторный вызов начинает запись с начала буфера.
Контракт сверён с исходниками закреплённой версии.
[Tokio 1.43: AsyncWriteExt::write_all](https://docs.rs/tokio/1.43.0/tokio/io/trait.AsyncWriteExt.html#method.write_all).

R3-03 и R3-04 опираются на правила TLS: сообщения могут объединяться в одной
записи или разбиваться на последовательные Handshake-записи; вклинивание записей
другого типа внутри сообщения запрещено. Парсер остаётся средством извлечения
имени, а не полной валидацией TLS. [RFC 8446, §5.1](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.1).

Открытые пункты:

**R3-12 — P1 — Временный users-файл на Windows может иметь более широкую DACL.**

Условие: основной файл защищён собственной DACL, а каталог допускает более
широкое наследуемое чтение. `OpenOptions::create_new` создаёт `.tmp` с DACL
каталога, затем записывает хеши пользователей. DACL основного файла переносится
только при ReplaceFileW. Следовательно, защита конечного имени не закрывает окно
доступа к временному файлу и к копии, оставшейся после аварии. Это вывод по коду
и правилу наследования, без динамической проверки ACL в этом раунде.
[users_file.rs:414](../crates/resocks5/src/config/users_file.rs#L414),
[правила Windows](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights).

Нужно задавать подходящий security descriptor при создании временного файла
до записи содержимого и проверять существующий и первый users-файл в каталогах
с разными DACL. Проверка изменения ACL временного каталога в предыдущем раунде
была отклонена автоматической проверкой разрешений с причиной `blocked by policy`;
повторная попытка обхода этого ограничения не выполнялась.

R2-14 поэтому закрыт лишь частично. Unix-тесты подтверждают `0600` для нового
файла и сохранение mode при замене; перенос владельца и группы по-прежнему
не реализован и явно исключён из текущего контракта.

**R3-13 — P3 — Вытеснение sticky cache остаётся линейным под общим mutex.**

При заполнении кэша новая цель вызывает `retain`, затем поиск минимального
`last_used`. При `C` записях это `O(C)` для вставки, блокирующее параллельные
попадания в кэш; стандартный лимит — 4096. Верхняя граница памяти исправна,
но частая смена целей сохраняет этот расход. Следующий шаг — отдельная структура
порядка вытеснения с ограниченной памятью и измерение реального профиля доступа.
Пункт продолжает R2-21. [rotator/mod.rs:81](../crates/resocks5-net/src/rotator/mod.rs#L81).

**R3-14 — P3 — Идентификаторы маршрутов копируют строки и учётные данные.**

Обратный индекс ротатора после конструирования неизменяем, но остаётся DashMap.
`index_of` создаёт новый tuple со строками host/user/password при каждой записи
успеха или отказа. Аналогичные клоны создаются для HashSet маршрутов и dead-list
в establish_connection. Желательны стабильные идентификаторы конфигураций и
чтение неизменяемого индекса без блокировки, с сохранением различий протокола
и аккаунта. Сортировка из R2-22 исправлена в R3-10; эта часть R2-22 остаётся.
[rotator/mod.rs:261](../crates/resocks5-net/src/rotator/mod.rs#L261),
[establish_connection.rs:149](../crates/resocks5/src/server/establish_connection.rs#L149).

используют живой fd, Windows-вызовы LockFileEx/UnlockFileEx — синхронный handle

Оценка расходов структурная. Проверка полноты TLS теперь обходит `R` заголовков
за `O(R)` без копирования payload; для одной записи это постоянная работа.
SNI из нескольких записей всё ещё требует сборки, а повторный разбор такого
растущего префикса может оставаться квадратичным по суммарным копированиям.
Лимит накопления 16 КиБ сохранён. Сортировка рейтингов остаётся `O(N log N)`,
но выполняется вне mutex и без промежуточного вектора весов. Новый численный
ключ требует дополнительных логарифмов; измеренного ускорения всего выбора
не заявляется. Нагрузочный стенд, p95/p99, RSS и процент ускорения не измерялись.
