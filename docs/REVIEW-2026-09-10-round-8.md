**R8-01 — P1 — Защита users-файла не распространяется на мигрируемые upstream-пароли.**

[load_or_init_proxy_list](../crates/resocks5/src/config/load_or_init.rs#L56)
читает прежние `socks5_ipv4_list.txt` / `socks5_ipv6_list.txt`, включая строки
`user:pass@host:port`, затем записывает `resocks5.proxy_list.ktav` через
`ktav::to_file`. В ktav 0.6.1 `src/lib.rs:147–150` это сериализация в строку
и обычный `std::fs::write`: режим исходных файлов не переносится, приватное
создание нового файла не запрашивается.

При обычном создании на Unix без дополнительного default ACL используются
права `0666`, ограниченные umask.
Таким образом, при `umask 022` новая копия получает `0644`, даже если старый
список с теми же паролями имел `0600`. Это следует из
[контракта OpenOptionsExt::mode](https://doc.rust-lang.org/std/os/unix/fs/trait.OpenOptionsExt.html#tymethod.mode).
Если другой локальный пользователь может пройти родительские каталоги,
он получает чтение новых credentials. Старый защищённый файл при этом
остаётся нетронутым, что не защищает уже созданную копию.

[SECURITY.md](../SECURITY.md#L95) прямо относит upstream credentials к
секретам в `.ktav` и запрещает их общедоступное чтение. Для users-файла уже
существует [приватный writer](../crates/resocks5/src/config/users_file.rs#L561),
но этот путь его обходит. Это отдельный файл и отдельный путь от ранее
исправлявшегося R2-14. Конкретное расширение прав на Windows здесь не утверждается.

Создавать конфигурацию с credentials приватной с момента открытия файла,
включая промежуточные копии, и сохранять требуемую защиту при публикации.
Поздний chmod после записи оставит окно раскрытия. Критерий исправления:
при миграции защищённого списка новый файл и временные файлы не раскрывают
его содержимое дополнительным пользователям даже при разрешающем umask.

**R8-02 — P2 — Первоначальная запись двух конфигураций остаётся неатомарной.**

В [load_or_init_main](../crates/resocks5/src/config/load_or_init.rs#L31)
и [load_or_init_proxy_list](../crates/resocks5/src/config/load_or_init.rs#L56)
после `exists()` выполняется прямой `ktav::to_file` по окончательному имени.
Нет повторной проверки под межпроцессной блокировкой и нет атомарной
публикации подготовленного документа. Используемый `fs::write` создаёт файл
или заменяет его содержимое через `File::create` и `write_all`.
[Документация std::fs::write](https://doc.rust-lang.org/std/fs/fn.write.html).

Два конкретных сценария:

1. Первый процесс создал main-файл, но ещё не записал документ. Второй видит
   существующий файл и читает его пустым/неполным. У MainConfig обязательны
   port и auth, поэтому второй запуск завершается ошибкой конфигурации.
2. Запись после создания файла завершается ошибкой либо процесс прекращается.
   Окончательное имя уже существует. Следующий запуск пытается читать остаток,
   а не повторять инициализацию или миграцию из оставшегося исходника.

Есть и гонка проверки отсутствия: процесс, ранее увидевший `exists() == false`,
позднее может затереть уже созданный другим процессом файл. Для
[users-файла](../crates/resocks5/src/config/load_or_init.rs#L92) такой класс
ошибок закрыт блокировкой, повторной проверкой и атомарной записью; остальные
две конфигурации этой защитой не пользуются. Параллельные CLI users-команды
тоже проходят эти ветки первоначальной инициализации.

Согласовать создание каждого файла между процессами и публиковать только
полный документ. Уже появившийся файл должен читаться, а не заменяться
устаревшим результатом проверки отсутствия. Критерий: параллельные первые
запуски не видят незавершённую конфигурацию, а ошибка записи не оставляет
частичный файл под окончательным именем. Это продолжение класса R2-04
в других ветках инициализации, без переоткрытия исправленного users-пути.

**R8-03 — P2 — SOCKS5 CONNECT не проверяет допустимость доменного назначения до dial.**

[Ветка ATYP=0x03](../crates/resocks5/src/server/handle_socks5_client.rs#L530)
принимает любую длину из одного байта, включая ноль, и проверяет у домена
только UTF-8. После согласования метода пакет CONNECT
`05 01 00 03 00 01 BB` превращается в target `:443`: длина домена равна нулю,
порт равен 443. Домен с NUL тоже остаётся допустимой Rust-строкой.

Для обычного SOCKS5-upstream сначала выполняется
[pool.acquire](../crates/resocks5-net/src/connect/connect_socks5_proxy.rs#L24),
потом greeting/auth, и лишь затем
[HostPort::parse](../crates/resocks5-net/src/connect/handshake_over_stream.rs#L62)
отвергает `:443`. [Учёт ошибки](../crates/resocks5/src/server/establish_connection.rs#L655)
штрафует исправный upstream и продолжает маршрутные попытки. В случае
управляющих байтов HTTP-upstream аналогично отвергает target уже после acquire.
При разрешённом anonymous credentials для этого не нужны; иначе условие —
успешная клиентская аутентификация.

RFC описывает DOMAINNAME как имя назначения, а не произвольный бинарный
буфер. [RFC 1928, §5](https://www.rfc-editor.org/rfc/rfc1928.html#section-5).
Здесь достаточное доказательство дефекта даёт и собственный поздний парсер:
вход, который заведомо не может пройти установление маршрута, расходует
upstream-соединения и изменяет общий рейтинг.

Проверять непустоту и допустимость доменного назначения при входном handshake,
до выбора маршрута; возвращать клиентскую SOCKS5-ошибку. Критерий: пустой
domain и запрещённые управляющие байты дают отказ без acquire, greeting
upstream и изменения рейтинга. Исправленная HTTP-валидация из R6-04 этот
отдельный входной путь не охватывает.

**R8-04 — P2 — Успешная установка длинного пароля делает SOCKS5-вход невозможным.**

[read_new_password](../crates/resocks5/src/cli/run_user_command.rs#L269)
проверяет только непустоту и совпадение двух вводов. `add` и `set-password`
сохраняют hash пароля длиннее 255 байтов и сообщают успех. Верхняя граница
из RFC 1929 уже проверяется у
[имени пользователя](../crates/resocks5/src/cli/run_user_command.rs#L297),
но не у пароля. [try_claim_init](../crates/resocks5/src/auth/state.rs#L204)
также проверяет только пустую строку, поэтому тот же пароль можно закрепить
за init-пользователем через HTTP.

Например, 256 ASCII-байтов допустимы для текущего Argon2-вызова и помещаются
в HTTP Basic, но не в SOCKS5 PASSWD: поле PLEN имеет один байт, а длина пароля
по протоколу — от 1 до 255 байтов.
[RFC 1929, §2](https://www.rfc-editor.org/rfc/rfc1929.html#section-2).
Это предел байтов, не количества Unicode-символов. Корректный SOCKS5-клиент
не способен передать установленный пароль полностью; его усечение изменит
проверяемый секрет и даст отказ.

Сделать ограничения общей учётной записи явными и едиными для CLI и первого
claim. Для учётной записи, предназначенной обоим протоколам, проверять
SOCKS5-предел до hash/persistence; если длинные пароли нужны только HTTP,
такое ограничение возможностей должно быть явно обозначено. Не усекать
пароли молча. Критерий: создание или смена SOCKS5-совместимого пароля
длиной 256 байтов не заканчивается ложным успехом, а границы 1 и 255
сохраняют работоспособность. Старые хеши этим ревью не менялись.

**R8-05 — P3 — Межпроцессный users-lock охватывает ещё и вывод результата в stdout.**

[commit_op_to](../crates/resocks5/src/cli/run_user_command.rs#L180) получает
`UsersFileLock`, читает свежую конфигурацию, применяет изменение и выполняет
`write_atomic`. Затем, ещё до уничтожения lock guard, вызывается `report(op)`
с синхронными `println!`.

Если stdout заблокирован потоком вывода или остановившимся получателем,
операция уже сохранена, но users-lock остаётся занят. Другие CLI-записи и
серверные init-claims ждут этот вывод либо исчерпывают время ожидания lock.
Даже без полного зависания скорость вывода ненужно увеличивает длительность
критической секции. Например, это проявляется при общей заполненной трубе
журнала автоматизации; одиночная короткая строка в пустой трубе обычно не блокируется.

Освобождать lock сразу после завершённой атомарной записи, а успех печатать
после выхода из защищённой секции. Сохранить порядок «сначала commit,
потом сообщение об успехе». Критерий: ожидающий вывод результата CLI
не удерживает блокировку users-файла.

**R8-06 — P3 — Работа с пользователями зависит от неиспользуемых main/proxy-list.**

[run_user_command](../crates/resocks5/src/cli/run_user_command.rs#L58)
вызывает общий `load_or_init`, который последовательно читает main,
proxy-list и users. После этого CLI использует только `configs.users`.
Таким образом, даже `users list` читает и разбирает весь список upstream,
создавая промежуточные строки и структуры, которые не нужны команде.

Объём лишнего чтения и буферов растёт с размером proxy-list: только чтение
его текста добавляет `O(B_proxy)` работы и памяти. Есть и функциональная
связность: ошибка синтаксиса в `resocks5.proxy_list.ktav` останавливает
`users list`, `disable` или `set-password` до обращения к исправному
users-файлу. Причина отказа относится к другой конфигурации.

Загружать для users-команд необходимое хранилище пользователей. Поддержку
первого запуска сохранить через существующую защищённую инициализацию users;
инициализацию остальных настроек отделить от разбора их существующего содержимого.
Критерий: чтение/изменение корректного users-файла не зависит от размера
или синтаксической ошибки неиспользуемого proxy-list. Выигрыш во времени
и памяти не измерялся; установлен сам устранимый путь чтения и аллокаций.

**R8-07 — P3 — Подготовка ротаторов копирует строки обычных прокси перед удалением оригиналов.**

В [run_server_inner](../crates/resocks5/src/main.rs#L262) обычные v4/v6-прокси
получаются через `iter().filter(...).cloned().collect()`. Для
[ProxyConfig](../crates/resocks5-net/src/types/proxy_config.rs#L13) Clone
копирует String-поля host и присутствующие credentials. Сразу после этого
`all_v6` и `all_v4` потребляются через `into_iter`, из них выбираются только
gates, а исходные обычные записи уничтожаются.

В результате для каждого обычного proxy descriptor выполнено ненужное
глубокое копирование перед тем, как оригинал стал доступен для перемещения.
У списков с аутентификацией копируются также username/password. Это расход
старта и временной памяти, а не дополнительная операция каждого туннеля.

Разделять принадлежащие функции записи через потребляющий обход, перемещая
их в v4/v6/gate-группы с сохранением порядка каждой группы. Обход остаётся
`O(N)`, но копирование содержимого строк для такого разделения не требуется.
Критерий: построение групп не вызывает Clone у обычных ProxyConfig,
а состав и порядок групп совпадают с текущими.

**R8-08 — P3 — UTF-8 для HTTP Basic не объявляется клиенту.**

Ответ [407](../crates/resocks5/src/http_proxy/handle_http_client.rs#L31)
содержит только `Proxy-Authenticate: Basic realm="resocks5"`. При этом
[декодер credentials](../crates/resocks5/src/http_proxy/handle_http_client.rs#L579)
жёстко требует UTF-8. CLI не ограничивает имя и пароль ASCII.

По RFC кодировка Basic без charset не определена однозначно; клиент может
использовать локальную кодировку, а при `charset="UTF-8"` переключиться на
UTF-8. Например, клиент с ISO-8859-1 отправит `é` как байт `E9`, который
текущий декодер отвергнет. Новый 407 опять не сообщает ожидаемую кодировку,
поэтому согласование не продвигается.
[RFC 7617, §2 и приложение B](https://www.rfc-editor.org/rfc/rfc7617.html#section-2).

Для поддерживаемого Unicode-профиля объявлять UTF-8 в challenge и согласовать
его с созданием и проверкой учётных данных. Учесть, что этот параметр также
задаёт ожидание NFC; нельзя менять смысл уже сохранённых паролей произвольным
преобразованием только на одной стороне проверки.
[RFC 7617, §2.1](https://www.rfc-editor.org/rfc/rfc7617.html#section-2.1).
Приоритет P3: параметр advisory, ASCII-клиенты и клиенты с UTF-8 по умолчанию
уже работают. Критерий улучшения: понимающий charset клиент успешно
аутентифицирует поддерживаемые не-ASCII credentials после challenge.

**Состояние прежних замечаний.**

Поскольку код после раунда 7 не менялся, **R7-01–R7-07 остаются открытыми**:
recovery после deadline, прогресс TLS flush, общий слот auth во время claim,
недостоверные чередования в тестах claim, счётчики без проверки payload,
production atomic для теста и начало измерения teardown после spawn.
Их доказательства и критерии сохранены в
[отчёте раунда 7](REVIEW-2026-09-10-round-7.md).

Ранее описанный **R5-09 — P3** с полной сортировкой при малом оставшемся
бюджете также не закрыт. Эти пункты не включены повторно в восемь
дополнительных замечаний выше. Исправленные приватная запись users-файла,
редактирование его актуального состояния под lock и экранирование логов
не переоткрываются: R8-01/R8-02 касаются других путей записи, R8-05 — границы
критической секции, а не атомарности сохранения пользователей.

Приоритет дальнейшей работы: приватность миграции (R8-01), надёжность
первоначальных конфигураций и входная валидация (R8-02–R8-04), затем
короткая критическая секция CLI, ненужные чтения/копии и совместимость Basic
(R8-05–R8-08). Исходники, версии и рабочие конфигурации в этом раунде не менялись.
