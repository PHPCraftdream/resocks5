# План восстановления после потери локального репозитория — 2026-09-19

## Что произошло

Локальный репозиторий `D:\dev\rust\resocks5` был случайно удалён до того, как
работа раундов 6, 7 и 8 (код-ревью и их исправления) была запушена в
`origin/main`. Репозиторий переклонирован из `PHPCraftdream/resocks5` (GitHub).
`origin/main` остановлен на коммите `2b4ef7a` — это конец раунда 5.

**Всё, что было сделано между `2b4ef7a` и моментом удаления, потеряно из
истории git безвозвратно** (не было push, не было `git reflog` — весь `.git`
удалён). Восстанавливается по памяти текущей рабочей сессии: каждый дифф был
лично вычитан построчно при zero-trust верификации в момент, когда работа
делалась, поэтому механизм каждого фикса воспроизведён с высокой точностью.

**Изменённый процесс на время восстановления:** коммитить и **пушить сразу**
после каждого смерженного блока (не откладывать пуш до конца всей работы) —
единственная реальная защита от повтора этой потери.

## Порядок восстановления (по цепочкам файлов, с зависимостями)

Все задачи заведены в TaskList (`#50`–`#68`), каждая — самодостаточное
описание с точным механизмом фикса, критериями приёмки и тестами.
Независимые от 2b4ef7a цепочки (могут стартовать параллельно):

```
#50 (R6-04+06, handle_http_client.rs)
  → #56 (R6-03, handle_client+socks5+http) → #59 (R6-07 handle_client part)
                                            → #60 (R7-01+R8-03+R8-08)

#51 (R6-01+05, auth/state.rs)
  → #61 (R6-07 auth part) → #62 (R7-03) → #63 (R8-04) → #64 (R7-04)
                                              ↳ #68 (R8-05+R8-06, cli/run_user_command.rs)

#52 (R6-02, tls_fragment+forward_tunnel)
  → #65 (R7-02) → #66 (R7-05)
                → #67 (R7-02-followup, upstream_tls/any_upstream/connect_proxy)

#53 (R6-08, rotator+establish_connection) → #57 (R7-06)

#54 (R8-01+02, load_or_init+users_file) — независима, P1, приоритет

```

Стратегия параллелизма (по памяти этой сессии): максимум 2 одновременных
`rush`-агента в изолированных `worktrees/`, с проверкой свободной памяти
(`wmic OS get FreePhysicalMemory`) перед каждой волной. Каждая задача
верифицируется zero-trust (debug+release тесты многократно, clippy, fmt,
`cargo semver-checks` для resocks5-net) лично перед мержем в `main`.

## Критический процессный момент

**Коммитить и пушить сразу после каждого смерженного блока.** Не копить
десятки локальных коммитов без push, как это произошло в исходной сессии —
именно это стало причиной полной потери работы при случайном удалении
директории.

## Известные фоновые обстоятельства (для контекста будущих сессий)

- Общий `sccache`-демон на этой машине нестабилен под конкурентной нагрузкой
  от посторонних процессов — падает с `STATUS_STACK_BUFFER_OVERRUN`
  (`0xc0000409`). Обход: `RUSTC_WRAPPER=""` перед командой cargo.
- Argon2id-хеширование в тестах `auth/state.rs` может занимать секунды (не
  ~15мс) под реальной CPU-нагрузкой от параллельных cargo-процессов —
  wall-clock границы в тестах должны иметь щедрый запас (секунды, не сотни
  миллисекунд), с пояснением выбранной границы в комментарии.
