**R4-01 и R4-02: механизм и воспроизведение.** У прежней кучи `shed_stale`
останавливался на первом актуальном элементе. Холодный ключ удерживал этот
элемент на вершине, а каждое чтение горячего ключа добавляло новую запись.
Проверка актуальности поколения не учитывала TTL холодного ключа. Поэтому
его истечение само по себе не освобождало накопленную историю. Позднейшая
вставка могла разбирать эту историю под общим mutex.

Теперь порядок принадлежит самому приватному `StickyCache`. Конструктор
заменил литералы структуры в тестах; их прежний набор полей не является
ограничением публичного API. `HashMap` и оба `BTreeSet` разделяют один
`Arc<str>` на адрес. Обновление удаляет старую индексную запись, удаление
ключа очищает оба индекса. Для новой записи достаточно освободить одно место;
полного прохода по кэшу нет. Дополнительно проверены обновление TTL при
замене, освобождение метаданных при удалении и LRU при одинаковых timestamps.

| Регрессия | Короткий сценарий | До исправления | После |
|---|---|---|---|
| [Ограничение метаданных](../crates/resocks5-net/src/rotator/mod.rs#L576) | Два ключа, восемь чтений одного из них | 10 записей вытеснения при лимите 2 ключа | 4 индексные записи, независимо от истории обращений |
| [TTL перед LRU](../crates/resocks5-net/src/rotator/mod.rs#L593) | TTL 10 с; первый ключ вставлен в t=0, второй в t=5; чтение первого в t=9; вставка третьего в t=11 | Второй, ещё действующий ключ терялся | Сохраняются второй и третий ключи |
| [NUL в пути](../crates/resocks5/src/config/users_file.rs#L877) | К уникальному имени добавлены NUL и суффикс | Helper возвращал успех вместо `InvalidInput` и создавал файл по префиксу | Ошибка как у `OpenOptions`, файл по префиксу отсутствует |
| [Длинный путь](../crates/resocks5/src/config/users_file.rs#L902) | Три вложенных имени каталогов по 80 символов | `std::fs` создавал файл; helper возвращал Windows error 3 | Создание, первая запись users-файла, замена и чтение результата проходят |

Все четыре случая действительно падали на неисправленном коде перед
исправлением. Это небольшие регрессионные проверки, без нагрузочного прогона.

**R4-03 и R4-04: сохранённая идентичность.** Ключ определяется полями
`host`, `port`, `protocol`, `user`, `password`, `is_gate`. Поле `gate`
описывает маршрут и исключено из идентичности самого upstream. Поэтому
запись из sticky cache с добавленным gate попадает в тот же рейтинг, что
и исходная конфигурация. Хеш служит для поиска кандидатов; совпадение хеша
не заменяет сравнение полей. Проверены принудительная коллизия, последнее
вхождение повторяющейся конфигурации и различие маршрутов по аккаунтам
и gate. Проходят и существующие интеграционные тесты бюджета попыток
и атрибуции gate-отказов.

Обозначения для оценки затрат: `C` — лимит ключей кэша, `M` — накопленная
история обращений, `N` — число настроенных прокси, `A` — число уже испытанных
маршрутов. Оценки хеш-поиска ожидаемые; длина ключа считается фиксированной.

| Операция / ресурс | До | После |
|---|---|---|
| Метаданные кэша | `O(M)`, лимит ключей их не ограничивал | `O(C)` |
| Обновление порядка / вытеснение | Работа с кучей размера `M`; возможен разбор множества старых элементов под mutex | Ограниченное число операций `O(log C)` с индексами |
| Владение порядком кэша | Внешний mutex плюс общий `Arc<Mutex<LruBook>>`, хранящийся в записях | Один mutex вокруг всего кэша |
| Поиск рейтингового слота | `O(N)` | Ожидаемо `O(1)`, без копирования строк и без mutex |
| Проверка испытанного маршрута | `O(A)` за проверку | Ожидаемо `O(1)` |

Для малых списков хеширование имеет собственную стоимость. Эти изменения
устраняют рост сложности и неограниченную историю; измеренного выигрыша
в latency/throughput отчёт не заявляет. Стандартный бюджет попыток равен 10;
R4-04 сильнее проявляется при его увеличении. Общий mutex кэша остаётся,
а операции деревьев могут выделять память для узлов в пределах `O(C)`.

**R4-05–R4-07: Windows и FFI.** Прямой Win32-вызов не выполняет всю подготовку
пути, которую делает `std::fs`. Для обычного `CreateFileW` действует ограничение
MAX_PATH без специального префикса или системного opt-in.
[Контракт CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).
Нормализация выполняется до добавления `\\?\`, поскольку verbatim-путь меняет
обработку разделителей и компонентов. Использована стандартная
[std::path::absolute](https://doc.rust-lang.org/std/path/fn.absolute.html), доступная
с Rust 1.79. Отдельный тест проверяет преобразование длинного UNC-пути
с `..` и сохранение готового verbatim-пути.
