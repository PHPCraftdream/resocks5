**R2-14 — P1 — Атомарная замена не сохраняет защитные атрибуты файла пользователей.**
[users_file.rs:41](../crates/resocks5/src/config/users_file.rs#L41).
`File::create` создаёт `.tmp`, после чего он заменяет существующий файл.
Права исходного файла не переносятся. На Unix конкретный сценарий: защищённый
файл `0600`, отсутствующий `.tmp`, `umask 022` — новый файл создаётся с `0644`
и становится файлом пользователей вместе с этими правами. Значения по умолчанию
подтверждены [OpenOptionsExt::mode](https://doc.rust-lang.org/std/os/unix/fs/trait.OpenOptionsExt.html#tymethod.mode).

На Windows требуется отдельно сохранять DACL и другие нужные атрибуты:
проверенный исходник `std::fs::rename` в используемом toolchain вызывает
`MoveFileExW`, а не операцию с гарантией переноса метаданных заменяемого файла.
Для сравнения, [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)
описывает сохранение DACL, но выбранная реализация должна учитывать также
частичные ошибочные исходы этого API. Простая замена одного имени функции
не является достаточным проектом исправления.

Пункт установлен статически. Команду динамической пробы ACL во временном
каталоге автоматическая проверка разрешений отклонила с `blocked by policy`,
без уточнённой причины; проба не запускалась. Критерий закрытия: права/DACL
после сохранения совпадают с требуемыми исходными, а временный файл не раскрывает
данные в промежутке до замены. Проверять отдельно на целевых платформах.

**R2-15 — P2 — Lock-файл остаётся после аварийного завершения владельца.**
[acquire:91](../crates/resocks5/src/config/users_file.rs#L91),
[Drop:123](../crates/resocks5/src/config/users_file.rs#L123).
Исключительность реализована наличием файла, а его удаление — только в Drop.
При аварийном завершении/выходе без деструкторов файл остаётся: следующие записи
упираются в десятисекундный таймаут до ручного удаления. Сам по себе таймаут
не доказывает, что владелец умер. Семантика отсутствия деструкторов при выходе
описана в [std::process::exit](https://doc.rust-lang.org/std/process/fn.exit.html).
Нужна блокировка, освобождаемая ОС при завершении процесса, либо строго
обоснованная схема восстановления владения. Проверять завершение отдельного
процесса с удерживаемой блокировкой и успешную последующую запись без ручной очистки.

**R2-16 — P2 — `sync_all` временного файла не завершает гарантию сохранности rename.**
[users_file.rs:51](../crates/resocks5/src/config/users_file.rs#L51).
После синхронизации содержимого вызывается rename, но каталог не синхронизируется.
Атомарная видимость для других процессов и сохранность нового имени после
аварии питания — разные свойства. Для POSIX различие явно описано в
[fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html).
Нужно определить обещанную модель сохранности и синхронизировать нужные метаданные.
Отказ после rename уже нельзя трактовать как доказательство неизменности старого
файла: требуется учитывать неопределённый исход фиксации. Тест отключения одного
процесса без сбоя ОС этого свойства не проверяет.

**R2-17 — P2 — Распознанная сигнатура не означает фрагментацию всего ClientHello.**
[forward_tunnel.rs:41](../crates/resocks5/src/server/forward_tunnel.rs#L41).
Накопление завершается, как только известны шесть байтов сигнатуры. Если очередное
чтение принесло только их, фрагментируется этот короткий префикс, а оставшийся
ClientHello передаётся обычным `copy_bidirectional`; SNI может целиком попасть
в неразбитый остаток. R2-06 исправляет путь начального pipelined-префикса, но
не устраняет этот механизм. Нужен учёт границ сообщения/записей на всём
ClientHello. Критерий: при разбиении после шестого байта и до SNI сохраняются
и полная последовательность байтов, и заданные границы всех её фрагментов.

**R2-18 — P2 — SNI-парсер не собирает handshake из нескольких TLS-записей.**
[parse_sni:36](../crates/resocks5-net/src/connect/recover_host.rs#L36),
[probe:169](../crates/resocks5-net/src/connect/recover_host.rs#L169).
Код снимает первый пятибайтовый заголовок и дальше считает весь буфер непрерывным
handshake. Заголовок следующей TLS-записи попадает в разбираемое тело; probe также
сравнивает длину сырых данных с длиной handshake без учёта дополнительных заголовков.
Между тем [RFC 8446, §5.1](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.1)
разрешает разбиение handshake по нескольким записям. Нужны разбор record layer
и тесты пересечения session-id, extensions и server-name границами TLS-записей.
Тесты разных TCP-чтений одного готового record не покрывают этот случай.

**R2-19 — P2 — Классификация gate-отказов применяется не ко всем путям.**
[cached-путь:379](../crates/resocks5/src/server/establish_connection.rs#L379),
[dead_gates:457](../crates/resocks5/src/server/establish_connection.rs#L457).
Ошибка cached-маршрута через gate всё ещё штрафует конечный proxy, даже если
`GateStage::GateConnect` показывает, что его не достигли. В новом переборе
`dead_gates` пополняется внутри вложенного цикла, но проверяется только при входе
во внешний: тот же недоступный gate может снова проверяться с другим proxy.
Нужна единая обработка исходов cached/нового маршрута и реальное прекращение
перебора комбинаций с доказанно неработающим gate. Проверять рейтинг нетронутого
proxy и число TCP-попыток к одному gate в пределах запроса. Это оставшаяся часть
замечаний R18/R19 первого раунда.

**R2-20 — P2 — Валидатор допускает параметры с нечисловыми производными весами.**
[policy.rs:45](../crates/resocks5-net/src/rating/policy.rs#L45),
[validate:55](../crates/resocks5-net/src/rating/policy.rs#L55).
Конечность отдельных полей недостаточна. Например, `min_weight = 1e-310`
положителен и проходит проверки диапазона, но `1.0 / min_weight` переполняется;
`k` становится бесконечным, а свежий вес `exp(-k * 0)` — NaN. Формула проверена
отдельным вычислением; это не результат нагрузочного теста. Нужны устойчивые
формулы и проверка допустимости производных значений, включая крайние конечные
параметры. Обычные значения по умолчанию этим примером не затронуты.

**R2-21 — P3 — Ограничение sticky-кэша добавило общий Mutex и линейное вытеснение.**
[insert:81](../crates/resocks5-net/src/rotator/mod.rs#L81),
[sticky:153](../crates/resocks5-net/src/rotator/mod.rs#L153).
Устранён неограниченный рост памяти, но при заполненном кэше новый адрес вызывает
`retain`, затем поиск минимального `last_used` по карте. Это `O(C)` под общим
Mutex; попадания в кэш тоже берут его для обновления времени. При потоке новых
адресов стоимость зависит от полного лимита кэша, а не от числа нужных записей.
Нужны измерения на соответствующем профиле использования и структура с дешёвым
порядком вытеснения. В этом раунде нагрузка для такого измерения не создавалась.

**R2-22 — P3 — Идентичности маршрутов клонируют строки, а полный порядок сортируется под lock.**
[proxy_identity:32](../crates/resocks5-net/src/rotator/mod.rs#L32),
[upstream_id:78](../crates/resocks5/src/server/establish_connection.rs#L78),
[Ratings::pick_order:114](../crates/resocks5-net/src/rating/mod.rs#L114).
Исправление смешанных аккаунтов добавило в идентичности username/password,
однако их вместе с host клонируют при поиске индекса и проверке наборов маршрутов.
Неизменяемый reverse-index по-прежнему использует `DashMap`; построение всех
весов и сортировка `O(N log N)` остаются внутри Mutex рейтингов. Кандидаты:
стабильные компактные идентификаторы, поиск без копирования строк и выбор нужного
префикса вне критической секции. Сохранять независимость аккаунтов и вероятностные
свойства; не заменять модель на иной алгоритм только ради красивой сложности.
Это продолжающаяся часть R26/R27 первого раунда, а не новый измеренный bottleneck.
