# Дизайн

Термины — в глоссарии `README.md`. Интерфейсы ниже — эскизы: имена и подписи уточняются при реализации, смысл менять нельзя без записи в журнал решений.

## 1. Модель угроз

**От чего защищаемся.**

- Подмена TLS на нашем канале: провайдер, оборудование фильтрации, локальная сеть.
- Подмена TLS узлом цепочки по отношению к следующему HTTPS-узлу: мост видит наш поток к внутреннему узлу и может ответить за него своим ключом.
- Случайная деградация: узел, который должен работать по TLS, начинает работать открытым текстом из-за ошибки конфига или кода.

**От чего не защищаемся.**

- Подмена рядом с самим узлом (в его дата-центре): все каналы увидят один и тот же чужой ключ.
- Сговор узлов двух каналов. Два узла одного поставщика считаются независимыми.
- Компрометация машины, на которой работает resocks5.

**Следствие для реализации.** Проверка подписи TLS-рукопожатия обязательна во всех режимах, включая снятие ключа. Без неё перехватчик предъявит настоящий сертификат узла, не владея его закрытым ключом, и хэш совпадёт.

## 2. Ключ и ожидание

**Ключ узла** — SHA-256 от SPKI листового сертификата, запись `sha256/<base64 без переносов>`. SPKI, а не сертификат целиком: перевыпуск сертификата на тот же ключ пин не ломает.

**Ожидание** — то, что клиент TLS требует от сертификата узла в одном рукопожатии:

| Часть ожидания | Смысл |
|---|---|
| `chain` (набор корней) | цепочка сертификата сходится к этим корням, имя совпадает |
| `pin` (ключ) | SPKI листа равен пину |
| `record` | принять любой сертификат, чтобы снять ключ |

Правило приёма: при `record` принимается любой сертификат; иначе достаточно, чтобы выполнилась хотя бы одна из заданных частей `chain` или `pin`. Если не задана ни одна часть, TLS-конфигурация не строится и соединение отказывает до открытия сокета.

Подпись рукопожатия проверяется всегда, одним и тем же кодом.

**Как ожидание выбирается для рабочего соединения:**

| Настройка узла | Режим `auto` | Режим `strict` |
|---|---|---|
| Ручной пин в конфиге | `pin` | `pin` |
| `ca_file` | `chain` (корни из файла) или сохранённый `pin` | то же |
| Ничего | `chain` (корни Mozilla) или сохранённый `pin` | сохранённый `pin`; без него отказ |

Свой CA считается в обоих режимах: это явное указание оператора, как и ручной пин.

**Запись ключа.** После успешного рабочего рукопожатия SDK сравнивает ключ узла с хранилищем. Ключа нет — записывает. Ключ другой (такое возможно, только когда сошлась цепочка) — записывает новый, старый уходит в историю, приложение пишет `WARN`. Запись делается после рукопожатия, а не внутри верификатора: в момент проверки сертификата подпись ещё не проверена.

## 3. Правило свидетельств

**Канал** — цепочка узлов до сверяемого узла N, по которой делается TLS-рукопожатие с N.

**Множество вмешательства канала** — узлы канала, способные подменить это рукопожатие:

- если в канале есть сверенный HTTPS-узел — последний такой узел и все узлы после него;
- если нет — все узлы канала.

Узлы до сверенного HTTPS-узла видят только шифртекст нашего соединения с ним и в множество не входят. Сам сверенный узел входит: он расшифровывает поток.

**Сила.**

| Свидетельство | Сила | Множество вмешательства |
|---|---|---|
| Канал со сверенным HTTPS-узлом | сильное | как определено выше |
| Доверенная цепочка сертификата N (свой CA — всегда; корни Mozilla — только в `auto`) | сильное | пустое |
| Канал без сверенного HTTPS-узла, включая рабочий путь узла | слабое | все узлы канала |

**Правило.**

1. Свидетельства независимы, если это разные наблюдения и их множества вмешательства не пересекаются. Доверенная цепочка независима от любого канала. Рабочий путь узла учитывается один раз.
2. **Первый ключ** принимается по двум независимым свидетельствам с одинаковым ключом, из которых хотя бы одно — не рабочий путь узла.
3. **Смена ключа** принимается по двум независимым свидетельствам с одинаковым ключом, из которых хотя бы одно сильное.
4. **Ручной пин** не меняется автоматически никогда.
5. Свидетельства показали разные ключи — отказ, запись в лог обоих ключей и путей, пин не пишется.

**Примеры.** `G` — открытый мост, `H` — сверенный HTTPS-узел, `V` — открытый проверочный узел, `N` — сверяемый узел.

| Свидетельство 1 | Свидетельство 2 | Множества | Первый ключ | Смена ключа |
|---|---|---|---|---|
| рабочий путь `N` | канал `H → N` | `{}` и `{H}` | да | да |
| рабочий путь `G → N` | канал `G → H → N` | `{G}` и `{H}` | да | да |
| рабочий путь `G → N` | канал `G → V → N` | `{G}` и `{G, V}` | нет: пересекаются | нет |
| рабочий путь `N` | канал `V → N` | `{}` и `{V}` | да, с `WARN` | нет: оба слабые |
| канал `H1 → N` | канал `H2 → N` | `{H1}` и `{H2}` | да | да |
| канал `H1 → N` | канал `H1 → V → N` | `{H1}` и `{H1, V}` | нет: пересекаются | нет |
| доверенная цепочка | рабочий путь любой | `{}` и любое | да | да |
| рабочий путь | рабочий путь | одно наблюдение | нет | нет |

Вторая строка — причина, по которой независимость считается через множество вмешательства, а не через «каналы без общих узлов»: при общем локальном мосте все каналы проходят через него, и простое правило запретило бы любую сверку.

Четвёртая строка — осознанная слабость: и рабочий путь, и канал через открытый проверочный узел может подменить тот, кто контролирует наш собственный канал связи. Для первого ключа это разрешено решением пользователя; для смены ключа запрещено.

## 4. Режимы и происхождение пина

`tls.pinning`:

- **`auto`** (по умолчанию). Доверенная цепочка по корням Mozilla считается свидетельством. Узел с публичным сертификатом работает с первого соединения, как до этих изменений. Обновление не блокирует существующие HTTPS-узлы.
- **`strict`**. Цепочка по корням Mozilla не считается. Каждый HTTPS-узел без ручного пина и без своего CA ждёт сверки по двум каналам.

Происхождение пина (`origin`):

| Значение | Как появился | Может ли смениться сам |
|---|---|---|
| `manual` | задан в `tls.nodes{…}.pin`; в файл пинов не пишется | нет |
| `ca` | цепочка к своему CA | да, пока цепочка сходится |
| `webpki` | цепочка к корням Mozilla, режим `auto` | да, пока цепочка сходится |
| `multipath` | сверка по каналам | только новой сверкой по правилу §3 |

## 5. Состояния HTTPS-узла в приложении

| Состояние | Когда | Клиенты |
|---|---|---|
| Сверен | есть пин (любого происхождения) | да |
| По цепочке | `auto` или свой CA, пина ещё нет | да; первое рукопожатие решает |
| Не сверен | `strict` без пина; цепочка не сошлась и пина нет; ключ не совпал с пином | нет: узел на паузе |

Переходы:

- «По цепочке» → «Сверен»: рукопожатие прошло, ключ записан.
- «По цепочке» → «Не сверен»: цепочка не сошлась (самоподписанный сертификат, узел по IP без IP SAN). SDK возвращает `Unverified`.
- «Сверен» → «Не сверен»: ключ не совпал с пином и цепочка не сошлась. SDK возвращает `PinMismatch`.
- «Не сверен» → «Сверен»: сверка по каналам прошла (S5b) либо оператор задал ручной пин и перезапустил сервер.

Блокировка несверенного узла держится на двух слоях. Гарантия — в SDK: без выполнимого ожидания TLS-конфигурация не строится. Экономия попыток — пауза в ротаторе: узел не выдаётся при выборе, поэтому клиентский запрос не тратит на него попытку. Пауза не зависит от карантина: карантин отключается настройкой `quarantine_threshold = 0`, а пауза обязана работать и тогда.

## 6. Конфиг

**Файл списка прокси.**

```text
https_v4: [
    user:pass@gw1.example.org:443
]
http_v4: [
    user:pass@203.0.113.30:443;plain_ok
]
socks5_v4: [
    *alice:secret@127.0.0.1:7890
    user:pass@203.0.113.7:1080
]

verify: {
    https_v4: [
        user:pass@v1.example.net:443
    ]
    socks5_v4: [
        user:pass@198.51.100.9:1080
    ]
}
```

- `verify` — отдельная структура с теми же шестью массивами, что и основные списки. Строки разбираются тем же кодом, включая метку `*` и флаг `;secure_only`.
- Узлы из `verify` никогда не получают клиентский трафик. У них свой ротатор и своя группа `verify` в файле здоровья.
- Проверочные узлы набираются так же, как выходы: через общие уровни мостов.
- `;plain_ok` на строке открытого списка разрешает порт 443 или 8443. Флаг стоит на самой строке по образцу `;secure_only`, поэтому не может ссылаться на несуществующий узел.

**Основной конфиг.** Все новые секции необязательны.

```text
tls: {
    transport: any
    pinning: auto
    verify_via_main: true
    nodes: {
        gw1.example.org:443: {
            sni: proxy.example.org
        }
        203.0.113.20:443: {
            pin: sha256/AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=
        }
        203.0.113.21:443: {
            ca_file: ca.pem
        }
    }
}

listen_tls: {
    enabled: false
    port: 8443
    cert: resocks5.tls.crt
    key: resocks5.tls.key
}
```

| Ключ | Значения | По умолчанию | Смысл |
|---|---|---|---|
| `tls.transport` | `any`, `tls-only` | `any` | `tls-only` требует HTTPS от всех узлов |
| `tls.pinning` | `auto`, `strict` | `auto` | см. §4 |
| `tls.verify_via_main` | `true`, `false` | `true` | разрешить сверенные HTTPS-узлы основных списков как верификаторы |
| `tls.nodes` | карта `host:port` → настройки | пусто | `sni`, `pin`, `ca_file`; действует на все строки с этим `host:port` в основных списках и в `verify` |
| `listen_tls.enabled` | `true`, `false` | `false` | входящий TLS |
| `listen_tls.port` | порт | `8443` | не должен совпадать с `port` |
| `listen_tls.cert`, `.key` | пути | рядом с конфигом | PEM-файлы |

Существующая секция `tls_fragment` начинает действовать и на наш ClientHello к HTTPS-узлам.

Точный синтаксис карты `tls.nodes` (ключ с двоеточием) нужно проверить на разборщике `ktav` в S5a; если ключ с двоеточием не разбирается, карта заменяется массивом объектов с полем `node`.

## 7. Файлы состояния

Рядом с конфигом, пишет только программа.

**`resocks5.pins.ktav`:**

```text
version: 1
tls_nodes: [
    gw1.example.org:443
]
pins: [
    {
        upstream: https://gw1.example.org:443
        server_name: proxy.example.org
        pin: sha256/…
        origin: multipath
        first_seen: 1763190000
        last_verified: 1763190000
        verified_via: [
            v1.example.net:443
            working-path
        ]
        history: [
            sha256/…
        ]
    }
]
```

- `tls_nodes` — память храповика: каждый `host:port`, который когда-либо стоял в списке `https_*`. Запись появляется при первом запуске с таким узлом и не зависит от того, записан ли уже пин. Удаляется только командой `pins forget`.
- Паролей и логинов в файле нет.
- `history` хранит не больше 8 прежних ключей.
- Ручной пин из конфига в `pins` не копируется: он действует, пока стоит в конфиге.
- Неизвестные поля не считаются ошибкой: старая версия программы должна прочитать файл новой.
- Запись атомарная, под той же межпроцессной блокировкой и с теми же правами, что файл `users`.
- Сервер пишет файл так: взять блокировку, прочитать файл, применить своё изменение, записать. Так правка из CLI не затирается.
- Правки из CLI действуют после перезапуска сервера, как у команды `users`.
- Файла нет, а HTTPS-узлы есть — строка `WARN` при запуске.

**`resocks5.health.ktav`** — как сейчас, плюс группа `verify`. Пауза несверенного узла в этот файл не пишется: она выводится из отсутствия пина.

## 8. Поведение приложения

**Запуск.**

1. Разбор конфигов. Строгие проверки (§9). Любая ошибка останавливает запуск до открытия порта.
2. Разбор списков, включая `verify`. Каждому HTTPS-узлу назначаются настройки TLS: `sni`, корни, ручной пин, хранилище пинов, режим.
3. Чтение файла пинов. Проверка храповика (§9).
4. Сборка ротаторов. HTTPS-узлы в состоянии «не сверен» ставятся на паузу.
5. Запуск первой сверки несверенных узлов в фоне.
6. Открытие портов.

**Выбор верификаторов для узла N.** Кандидаты перебираются по ярусам:

| Ярус | Кандидаты |
|---|---|
| 1 | Живые сверенные HTTPS-узлы основных списков, кроме N; только при `verify_via_main` |
| 2 | Узлы объекта `verify`: сначала сверенные HTTPS, затем открытые |
| 3 | Рабочий путь N — только как второе свидетельство |

- «Живой» — не в карантине и не на паузе.
- Внутри яруса порядок задаёт рандеву-хэш от пары (N, кандидат): для данного N порядок постоянен. Один оператор узла видит адреса малой постоянной части списка, а не всего списка.
- Канал строится так: уровни мостов, затем верификатор, затем рукопожатие с N.

**Сверка.**

1. Собрать первое свидетельство из яруса 1 или 2.
2. Собрать второе свидетельство из оставшихся кандидатов ярусов 1, 2, затем 3.
3. Передать оба в правило §3. Выполнено — записать пин с `origin: multipath`, снять паузу.
4. Не выполнено из-за пересечения или слабости — взять следующую пару.
5. Ключи разошлись — `ERROR`, узел остаётся на паузе, пин не пишется.
6. Кандидаты кончились — `ERROR`, узел остаётся на паузе.

Оба рукопожатия при сверке только снимают ключ: CONNECT не отправляется, логин и пароль узла N не отправляются.

**Повтор.** Отдельного таймера нет. Сверка запускается при запуске сервера и из существующего места, где при клиентском запросе запускаются пробы карантина. Между попытками для одного узла выдерживается пауза, растущая вдвое от `quarantine_initial_sec` до `quarantine_max_sec`; при успехе сбрасывается.

**Смена ключа.** Узел со `PinMismatch` уходит на паузу и сверяется заново по правилу для смены ключа. Старый пин остаётся в файле, пока новая сверка не пройдёт.

**Нагрузка.** Соединение через верификатор занимает разрешение пула этого узла, как существующие пробы. Нет свободного разрешения — кандидат пропускается, а не ждётся.

**Узел, видимый только через свой мост.** Независимого канала у него нет. Нужен ручной пин либо доверенная цепочка. `config check` перечисляет такие узлы.

## 9. Запрет деградации

**В SDK.** У узла есть признак `tls_only`. Узел с этим признаком и открытым протоколом отказывает ошибкой `PlaintextRefused` до открытия сокета. Проверка живёт в общей предпроверке узла, через которую проходят все пути соединения; в цепочке проверяются все узлы до первого сокета.

Признак относится к самому узлу: с ним говорим только по TLS. Открытый мост перед HTTPS-узлом допустим — поток к HTTPS-узлу идёт внутри TLS, а от подмены мостом защищает пин. Требовать HTTPS от всей цепочки нельзя: это запретило бы обычную схему «локальный мост → HTTPS-выход».

Не путать с существующими `allow_cleartext` и `secure_only`: они управляют отправкой пароля SOCKS5 и HTTP открытым текстом, а не транспортом.

**В приложении.** Каждый HTTPS-узел помечается `tls_only`. При `tls.transport: tls-only` помечаются все узлы, включая локальные мосты: режим означает «ни одного открытого узла».

**Ошибки запуска:**

| Проверка | Сообщение называет |
|---|---|
| Неизвестный ключ в основном конфиге или файле списка прокси | ключ |
| `tls-only`, а в основных списках, мостах или `verify` есть открытый узел | список и номер строки |
| Один `host:port` стоит в списках с разными протоколами | оба списка |
| Открытый узел на порту 443 или 8443 без `;plain_ok` | список и номер строки |
| Ключ `tls.nodes` не совпал ни с одним узлом | ключ |
| `listen_tls.port` равен `port` | оба значения |
| Храповик: `host:port` из `tls_nodes` файла пинов стоит в открытом списке | узел; подсказка `pins forget` |
| У узла в `tls.nodes` заданы одновременно `pin` и `ca_file` | ключ |
| Значение `pin` не разбирается как `sha256/<base64>` | ключ |
| `listen_tls.enabled`, а сертификат или ключ не читаются либо не соответствуют друг другу | путь к файлу |

Известные устаревшие ключи (`cb_*`, `gssapi_service`, `gssapi_protection`) остаются предупреждением, как сейчас.

Сообщения о строках списка не печатают саму строку: в ней логин и пароль.

**`resocks5 config check`** выполняет все проверки без запуска сервера и печатает таблицу узлов: протокол, транспорт, состояние пина и происхождение, доступные свидетельства. Код возврата ненулевой при любой ошибке. Сервер при запуске вызывает тот же код проверок.

## 10. Входящий TLS

- Отдельный порт `listen_tls.port`. Открытый порт работает как раньше.
- После TCP-accept читается первый байт. Не `0x16` — соединение закрывается без ответа. Перехода на открытый текст на этом порту нет.
- Дальше TLS-рукопожатие и обычная обработка клиента: тот же код, те же правила аутентификации. Basic остаётся запрещён там, где запрещён сейчас.
- Слот клиента (`max_concurrent_clients`) занимается на TCP-accept. Один срок клиента покрывает TLS-рукопожатие и согласование протокола.
- Версии TLS 1.2 и 1.3, клиентский сертификат не запрашивается, имя из ClientHello не используется.
- Сертификат и ключ читаются при запуске. Замена — перезапуск.
- Самоподписанный сертификат браузер не примет, пока его не импортируют; для своих клиентов печатается отпечаток (`resocks5 tls show`).

## 11. Ошибки SDK

Новые варианты `ConnectError`:

| Вариант | Когда | Сокет открыт | Вина узла | Ответ клиенту |
|---|---|---|---|---|
| `PlaintextRefused { protocol, endpoint }` | открытый узел с признаком `tls_only` | нет | нет | общий отказ |
| `Unverified { endpoint, got }` | нет выполнимого ожидания либо цепочка не сошлась и пина нет | нет либо закрыт | нет | узел недоступен |
| `PinMismatch { endpoint, expected, got }` | ключ не равен пину и цепочка не сошлась | закрыт | да, жёсткий отказ | узел недоступен |

`got` — снятый ключ, если рукопожатие дошло до сертификата. Сообщения ошибок печатают ключи и адрес узла, но не логин и не пароль.

Свойства, которые нельзя нарушить:

- `ProxyConfig.tls` и политика транспорта не участвуют в сравнении узлов (`same_upstream`, `upstream_hash`): личность узла — адрес, протокол, учётные данные и ранг.
- Подписи `dial`, `dial_chain`, `connect_chain`, `connect_proxy` не меняются. Коннектор, который в них передаётся, используется для узлов без `TlsOptions`.
- TLS-конфигурация узла кэшируется внутри `TlsOptions` по текущему пину. Сменился пин — строится новая конфигурация со своим кэшем сессий.
- Без feature `tls` ничего из перечисленного не существует, а HTTPS-узел по-прежнему даёт `TlsFeatureMissing`.

## 13. Известные ограничения

- Независимость каналов считается по узлам, а не по владельцам и сетям.
- В режиме `auto` узел с публичным сертификатом, набираемый напрямую, принимается по одному сетевому пути и удостоверяющему центру. Кому нужны два канала всегда, включает `strict`.
- Верификаторы узнают адреса сверяемых узлов. Рандеву-хэш уменьшает долю списка, видимую одному оператору, но не скрывает её.
- Правки файла пинов из CLI требуют перезапуска сервера.
- Сертификат входящего TLS не перечитывается без перезапуска.
