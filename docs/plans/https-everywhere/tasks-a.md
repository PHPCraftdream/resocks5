**Зачем.** Остальные задачи опираются на четыре предположения и на общую тестовую PKI. Проверить их дёшево сейчас и дорого посреди S2.

## S1. SDK: настройки TLS на узле

**Зависит от:** S0. **Крейт:** `resocks5-net`. **Ветка:** `s1-tls-options-<дата>`.

**Зачем.** Сегодня у всех узлов один клиент TLS, а имя для проверки сертификата всегда равно `host`. Из-за этого не работают узлы со своим CA, узлы за общим IP с другим именем и узлы, заданные IP-адресом. Эта задача даёт узлу собственные настройки TLS и вводит тип ключа, на который опираются S2 и S10.

**Сейчас.**

- `https_hop` (`connect/dial/chain.rs`) и `https_on_stream` (`connect/tls/upstream_tls.rs`) берут `ServerName::try_from(node.host)` и переданный `TlsConnector`.
- `check_tls` (`chain.rs`), `check_tls_slot` (`connect_proxy.rs`) и `dial_inner` (`dial/mod.rs`) требуют, чтобы для HTTPS-узла коннектор был передан.

**Сделать.**

1. `connect/tls/trust/`: тип `SpkiPin` — 32 байта, `Display` и `FromStr` в виде `sha256/<base64>`, конструктор из сертификата (`ParsedCertificate::subject_public_key_info` и `sha2`). Сравнение — за постоянное время не требуется: пин не секрет.
2. `connect/tls/trust/`: тип `TlsOptions` с закрытыми полями и построителем: `server_name`, `roots` (свой CA), необязательный криптопровайдер. Метод, который отдаёт готовый клиент TLS; клиент строится один раз и кэшируется внутри.
3. `types/proxy_config.rs`: поле `tls: Option<Arc<TlsOptions>>` под `#[cfg(feature = "tls")]` по образцу `secure_auth`; построитель `with_tls`. Обновить `new` и ручной `Debug` (печатать только факт наличия настроек).
4. В `https_hop` и `https_on_stream`: имя сервера — из настроек узла, иначе `host`; клиент TLS — из настроек узла, иначе переданный.
5. В `check_tls`, `check_tls_slot`, `dial_inner`: узел с собственными настройками TLS не требует переданного коннектора.
6. Документация: rustdoc на каждый публичный элемент; раздел в `crates/resocks5-net/README.md`.

**Интерфейс.** См. `design.md`, §12. В этой задаче у `TlsOptions` есть только `new`, `server_name`, `roots` и провайдер.

**Не делать.**

- Пины, хранилище, верификатор — это S2.
- Клиентский сертификат.
- Менять подписи `dial`, `dial_chain`, `connect_chain`, `connect_proxy`.
- Добавлять новые поля в `same_upstream` и `upstream_hash`.

**Ловушки.**

- `ServerName::try_from("203.0.113.5")` даёт IP-имя: SNI не отправляется, сертификат обязан содержать IP SAN. С заданным `server_name` проверяется уже это имя.
- Поле под `cfg` в `ProxyConfig`: проверь `clippy` без `tls`.
- Клиент TLS строится тем же способом, что в `make_tls_connector`: обычный построитель либо явный провайдер. Не вызывай `install_default`.
- `proxy_config.rs` — 752 строки; тесты нового поля клади в существующий тестовый модуль экономно.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| Узел с `server_name`, сертификат выдан на это имя, `host` — IP | рукопожатие проходит; стаб видит в ClientHello заданное имя |
| Тот же узел без `server_name` | ошибка TLS |
| Узел со своим CA, коннектор по умолчанию не передан | рукопожатие проходит |
| Узел со своим CA, сертификат подписан другим CA | ошибка TLS |
| Узел без настроек TLS | поведение прежнее, действующие тесты зелёные |
| Настройки на первом, среднем и последнем узле цепочки | каждый узел проверяется своими настройками |
| Путь с пулом (`connect_proxy`, `connect_chain`) и без пула (`dial`, `dial_chain`) | одинаковый результат |
| `SpkiPin`: печать, разбор, разбор мусора | круговой тест; ошибка на мусоре |
| `SpkiPin` из сертификата | равен значению, посчитанному тестовой PKI независимо |
| Два узла с одинаковым адресом и разными `TlsOptions` | `same_upstream` считает их одним узлом |

## S11. SDK: запрет открытого транспорта

**Зависит от:** S1. **Крейт:** `resocks5-net`. **Ветка:** `s11-tls-only-<дата>`.

**Зачем.** Узел, который обязан работать по TLS, не должен получить ни байта открытым текстом — даже если из-за ошибки конфигурации его протокол записан как SOCKS5 или HTTP. Проверка должна стоять в одном месте и срабатывать до открытия сокета.

**Сейчас.**

- Общая предпроверка `ProxyConfig::preflight_auth` вызывается в `dial_inner`, в `hop`, в `http_connect_handshake` и в ядре SOCKS5.
- На пути с пулом сокет берётся раньше: `connect_proxy`, `connect_http_proxy`, `connect_socks5_proxy`, `connect_https_proxy`, `connect_chain`, `connect_hedged` сначала вызывают `pool.acquire`.

**Сделать.**

1. `ProxyConfig`: поле `tls_only: bool` (по умолчанию `false`) и построитель `tls_only()`. Поле существует без feature `tls`.
2. `ConnectError::PlaintextRefused { protocol, endpoint }`: текст, три функции классификации в `error/classify.rs` (не вина узла, клиенту — общий отказ), тесты в `error/tests.rs`.
3. Новая предпроверка `preflight`: сначала транспорт (узел с `tls_only` и протоколом не `Https` — отказ), затем существующая `preflight_auth`. Заменить четыре вызова `preflight_auth` на `preflight`.
4. Вызвать `preflight` до `pool.acquire` во всех функциях пути с пулом. В `connect_chain` — для каждого узла цепочки до первого `acquire`.
5. В цепочках без пула проверить все узлы до первого сокета: добавить вызов в `check_tls` либо рядом с ним.

**Правило для цепочки.** Политика относится к самому узлу: с узлом `tls_only` говорим только по TLS. Открытый мост перед HTTPS-узлом допустим: поток к HTTPS-узлу идёт внутри TLS, а от подмены мостом защищает пин (веха B). Требовать HTTPS от всех узлов цепочки нельзя: это сломает обычную схему «локальный мост → HTTPS-выход».

**Не делать.**

- Менять поведение `allow_cleartext` и `secure_only`: это другая проверка.
- Трогать `handshake_over_stream` и `socks5_handshake`: у них нет `ProxyConfig`, поток даёт вызывающий.

**Ловушки.**

- У `preflight_auth` ранние выходы для `secure_only` и для `Https`: проверка транспорта должна стоять до них, иначе она недостижима.
- После переноса предпроверки перед `acquire` разрешение пула не должно браться при отказе — это часть приёмки.
- `connect_hedged` запускает попытки через замыкание; убедись, что отказ одной попытки не занимает разрешение и не ломает остальные.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| Каждая публичная функция соединения (`dial`, `dial_plain`, `dial_tcp`, `dial_chain`, `dial_chain_over`, `connect_chain`, `connect_proxy`, `connect_proxy_once`, `connect_http_proxy`, `connect_socks5_proxy`, `connect_hedged`) × узел {SOCKS5, HTTP} с `tls_only` | `PlaintextRefused`; считающий листенер: 0 соединений, 0 байт |
| Те же функции пути с пулом | разрешение пула не занято, тёплый сокет не израсходован |
| Цепочка, где `tls_only` стоит на среднем открытом узле | отказ до первого сокета к первому узлу |
| Цепочка «открытый мост → HTTPS-выход с `tls_only`» | соединение проходит |
| HTTPS-узел с `tls_only`, стаб обрывает TLS-рукопожатие | ошибка TLS; на открытом листенере того же порта 0 байт CONNECT |
| HTTPS-узел с `tls_only`, сборка без feature `tls` | `TlsFeatureMissing`, 0 соединений |
| Узел без `tls_only` | поведение прежнее |

Список функций в первом тесте сверяется с `connect/mod.rs`: если там появилась новая публичная функция соединения, она добавляется в тест.

## S6. Входящий HTTPS

**Зависит от:** S0. **Крейт:** `resocks5`. **Ветка:** `s6-listen-tls-<дата>`.

**Зачем.** Клиент должен иметь возможность дойти до самого resocks5 по TLS: тогда логин, цель и трафик не видны на участке от клиента до сервера.

**Сейчас.**

- `run_server` (`server/run_server.rs`) открывает один `TcpListener`, берёт слот клиента, считает срок клиента и запускает `handle_client`.
- `handle_client` и четыре обработчика за ним (`handle_socks5_client/negotiate.rs`, `recover.rs`, `http_proxy/handle_http_client/mod.rs`, `recovery.rs`) принимают `TcpStream`.
- `resocks5_net::server::accept_with` обобщён по потоку.

**Сделать.**

1. `server/handle/`: тип клиентского потока — перечисление «открытый TCP» и «TLS поверх TCP» с реализацией `AsyncRead` и `AsyncWrite`, методами `peer_addr` и `set_nodelay`.
2. Заменить `TcpStream` на этот тип в подписях `handle_client`, `global_allowed` и четырёх обработчиков. Тесты этих модулей оборачивают свой `TcpStream` в открытый вариант.
3. Конфиг: превратить `config/main/tls_fragment_config.rs` в каталог `config/main/tls/`; добавить секцию `listen_tls` (`enabled`, `port`, `cert`, `key`) с `serde(default)` и поле в `MainConfig`.
4. Загрузка при запуске: прочитать PEM-файлы, собрать серверную конфигурацию TLS без клиентской аутентификации. Нечитаемый файл или несоответствие сертификата и ключа — ошибка запуска с путём к файлу.
5. `run_server`: при `listen_tls.enabled` открыть второй листенер. Общую часть приёма (слот, keepalive, срок, запуск задачи) вынести в одну функцию для обоих портов.
6. В задаче клиента на TLS-порту, в пределах срока клиента: глобальный фильтр адресов; чтение первого байта без извлечения (`peek`); не `0x16` — закрыть; TLS-рукопожатие; затем `handle_client`.
7. Строка в логе о запуске TLS-порта.
8. Документация: `docs/REFERENCE.md`, шаблон основного конфига в `config/load_or_init.rs`.

**Не делать.**

- Клиентские сертификаты, ALPN, выбор по SNI, перечитывание сертификата без перезапуска.
- Менять правила аутентификации: внутри TLS действует тот же код, что на открытом порту.
- Определять TLS на открытом порту: порты раздельные.

**Ловушки.**

- TLS-рукопожатие выполняется в задаче клиента, не в цикле приёма: иначе медленный клиент остановит приём.
- Слот клиента берётся до рукопожатия и освобождается при любом исходе.
- Закрытие записи на TLS-потоке отправляет `close_notify`. Обработчики восстановления (`recover.rs`, `recovery.rs`) опираются на полузакрытие TCP — проверь тестом, что туннель поверх TLS завершается корректно в обе стороны.
- `handle_client.rs` — 955 строк: новый код туда не помещается.
- Правка `REFERENCE.md` меняет вывод `resocks5 config`; его сверяют тесты `print_config_docs::`.
- Задача `release-behavior` запускает тесты по имени `handle_client::` в release-режиме: новые тесты этого модуля должны проходить и там.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| Клиент TLS с корнем сервера делает CONNECT через порт `listen_tls` | туннель до эхо-цели работает в обе стороны |
| Тот же сценарий с SOCKS5 внутри TLS | работает |
| Открытый CONNECT на порт `listen_tls` | соединение закрыто, ни байта ответа |
| Мусор, начинающийся с `0x16` | рукопожатие сорвано, слот освобождён |
| Клиент открыл TCP и молчит | по сроку клиента соединение закрыто, слот освобождён |
| Достигнут `max_concurrent_clients` | новое соединение на TLS-порт сброшено без рукопожатия |
| Адрес клиента вне `allowed_clients` | отказ до TLS-рукопожатия |
| Аутентификация, запрещённая на открытом порту | так же запрещена внутри TLS |
| Полузакрытие со стороны клиента и со стороны цели поверх TLS | данные доставлены, туннель закрыт без ошибки |
| `enabled: true`, файла ключа нет | сервер не запускается, сообщение называет путь |
| Сертификат и ключ не соответствуют | сервер не запускается |
| `listen_tls.port` равен `port` | сервер не запускается |
| `enabled: false` | второго листенера нет, поведение прежнее |
| Вывод и ошибки | закрытого ключа в них нет |

## S10. CLI `tls`: сертификат и ключ сервера

**Зависит от:** S6, S1. **Крейт:** `resocks5`. **Ветка:** `s10-cli-tls-<дата>`.

**Зачем.** Входящему TLS нужны сертификат и ключ в отдельных файлах. Оператор должен получить их одной командой и уметь показать клиенту отпечаток.

**Сейчас.** Команды описаны в `cli/command.rs` (`Users`, `Config`), образец работы с файлом под блокировкой — `cli/run_user_command.rs`. Атомарная запись с правами `0600` и DACL на Windows — `config::users_file::write_atomic_text`.

**Сделать.**

1. `rcgen` становится обычной зависимостью приложения.
2. `cli/keys/`: модуль с командами. Группа `Tls { action }` в `cli/command.rs` и ветка в `main.rs`.
3. `resocks5 tls init [--name <имя или IP>]… [--force]`: самоподписанный сертификат и ключ в файлы из `listen_tls.cert` и `listen_tls.key`. Имена по умолчанию: `localhost`, `127.0.0.1` и `listen_host`, если это конкретный адрес. Без `--force` существующие файлы не перезаписываются. В конце печатается отпечаток.
4. `resocks5 tls show`: отпечаток `sha256/<base64>` через `SpkiPin` из SDK и пути к файлам.
5. `resocks5 tls check`: файлы читаются, сертификат и ключ соответствуют друг другу. Ненулевой код при ошибке.
6. Документация: `docs/REFERENCE.md`, включая абзац о том, что самоподписанный сертификат браузеру нужно импортировать.

**Не делать.**

- Команду `rotate`: замена — `init --force` и перезапуск.
- Новый разборщик X.509 ради срока действия и имён. Если их можно показать средствами уже имеющихся зависимостей — показать; если нет — не показывать.

**Ловушки.**

- Ключ пишется тем же кодом, что файл `users`, чтобы получить те же права доступа.
- Команды не запускают сервер и не требуют корректного списка прокси, как `users`.
- Теперь `rcgen` попадает в сборку под `musl` и в `cargo about`: проверь задачи `portable-builds` и `third-party-licenses`.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| `init`, затем загрузка этих файлов листенером S6 | клиент TLS с этим сертификатом в корнях подключается |
| `init` при существующих файлах без `--force` | отказ, файлы не изменены |
| `init --force` | новая пара, отпечаток другой |
| `show` | отпечаток равен значению, посчитанному тестом независимо |
| `check` на паре из `init` | нулевой код |
| `check` на ключе от другой пары | ненулевой код |
| `check`, `show` без файлов | ненулевой код, сообщение называет путь |
| Вывод всех команд | закрытого ключа нет |
| Права на файл ключа | только владелец (Unix: `0600`) |

## S12. Строгий конфиг, `tls-only`, `config check`

**Зависит от:** S11, S6. **Крейт:** `resocks5`. **Ветка:** `s12-strict-config-<дата>`.

**Зачем.** Возможности S1 и S11 бесполезны, пока оператор не может их включить и пока ошибка в конфиге проходит молча. Эта задача подключает их к конфигу и делает ошибку конфига остановкой запуска.

**Сейчас.**

- Неизвестный ключ конфига отбрасывается при разборе без сообщения. Устаревшие `cb_*` и `gssapi_*` ищутся текстом и дают предупреждение (`warn_obsolete_cb_keys`, `warn_obsolete_gssapi_keys` в `startup.rs`).
- Протокол узла определяется списком в `run_server_inner`; флаг строки `;secure_only` снимается в `split_secure_only_option`.
- `has_https` считается по спискам `https_v4` и `https_v6`.
- `resocks5 config` печатает справочник.

**Сделать.**

1. `#[serde(deny_unknown_fields)]` на `MainConfig`, всех его секциях в приложении и на `ProxyListConfig`. Файлы `users` и `health` не трогать.
2. Секция `pool` описана типом SDK `PoolConfig`. Не меняй тип SDK: заведи в приложении строгую секцию с теми же полями и преобразуй её в `PoolConfig`.
3. Устаревшие ключи `cb_*`, `gssapi_service`, `gssapi_protection` должны остаться предупреждением. Список бывших ключей `cb_*` восстанови по истории git. Способ на выбор: поля-заглушки, которые принимают и игнорируют значение, либо удаление этих ключей из разобранного документа до строгого разбора.
4. Секция `tls` в `config/main/tls/`: `transport` (`any` по умолчанию, `tls-only`), `nodes` — карта `host:port` → `sni`, `ca_file`.
5. Флаг строки `;plain_ok`: обобщить разбор флагов строки. Неизвестный флаг делает строку некорректной, как сейчас.
6. Проверки — чистая функция в `config/proxy_list/`: на входе разобранные конфиги, на выходе список проблем. Правила — `design.md`, §9, кроме храповика (S5a) и проверок `listen_tls`, сделанных в S6.
7. Запуск: вызвать проверки до открытия порта; при проблемах остановиться и напечатать все, а не первую.
8. Запуск: назначить узлам настройки. Каждый HTTPS-узел получает `tls_only`; при `tls-only` — каждый узел. Узлы из `tls.nodes` получают `TlsOptions` (`sni`, корни из `ca_file`).
9. `has_https`: клиент TLS по умолчанию создаётся, если HTTPS-узел есть в любом списке.
10. Команда `resocks5 config check`: `Config` получает необязательную подкоманду; без неё поведение прежнее. `check` загружает конфиги без создания файлов по умолчанию, вызывает те же проверки, печатает таблицу узлов (список, номер строки, адрес без логина и пароля, протокол, транспорт, настройки TLS) и возвращает ненулевой код при проблемах. Некорректная строка списка в `check` считается проблемой.
11. Строка в логе при запуске: режим транспорта и число узлов по протоколам.
12. Документация: `docs/REFERENCE.md`; запись в `CHANGELOG.md` о том, что неизвестный ключ теперь останавливает запуск.

**Не делать.**

- Объект `verify`, `tls.pinning`, ручной пин, храповик — это S5a и S5b.
- Менять поведение запуска для некорректной строки списка: она по-прежнему пропускается с предупреждением.
- Печатать строки списка в сообщениях.

**Ловушки.**

- `config check` не должен создавать файлы: `load_or_init` создаёт конфиги по умолчанию, поэтому проверке нужен путь загрузки без создания.
- Ключ карты с двоеточием (`host:port`) нужно проверить на разборщике `ktav`. Если не разбирается — массив объектов с полем `node`; запиши выбор в `design.md`.
- `startup.rs` — 799 строк: новую логику выноси в `config/proxy_list/` и `config/main/tls/`.
- При `tls-only` локальный мост на `127.0.0.1` по SOCKS5 тоже считается нарушением. Это намеренно: режим означает «ни одного открытого узла».
- Сообщение об ошибке должно называть ключ. Номер строки — если его даёт разборщик (результат S0).

**Приёмка.**

| Тест | Ожидание |
|---|---|
| Лишний ключ в каждой секции основного конфига и в списке прокси (параметризованно по секциям) | ошибка, называет ключ |
| Конфиг без новых секций | загружается, поведение прежнее |
| Ключи `cb_*` и `gssapi_*` | предупреждение, запуск продолжается |
| `tls-only` и SOCKS5-узел, HTTP-узел, открытый мост | ошибка с именем списка и номером строки для каждого |
| `tls-only`, все узлы HTTPS | проходит |
| Один `host:port` в `http_v4` и `https_v4` | ошибка |
| Один `host:port` дважды в одном протоколе | не ошибка этой проверки |
| HTTP-узел на 443 без `;plain_ok` и с ним | ошибка; проходит |
| SOCKS5-узел на 8443 без флага | ошибка |
| HTTPS-узел на 443 | проходит |
| `;plain_ok` на HTTPS-узле | строка некорректна |
| Ключ `tls.nodes`, которому не соответствует узел | ошибка, называет ключ |
| Несколько проблем сразу | напечатаны все |
| Узел из `tls.nodes` с `sni` и `ca_file` | рукопожатие со стабом проходит с этими настройками |
| HTTPS-узел после запуска | `tls_only` установлен |
| `config check` на исправном конфиге | нулевой код, таблица, файлов не создано |
| `config check` на конфиге с проблемами | ненулевой код, те же сообщения, что при запуске |
| `config` без подкоманды | печатает справочник, как раньше |
| Сообщения и таблица | логинов и паролей нет |
