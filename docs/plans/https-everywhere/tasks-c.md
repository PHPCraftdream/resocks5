## S3. SDK: правило свидетельств и снятие ключа

**Зависит от:** S2. **Крейт:** `resocks5-net`. **Ветка:** `s3-evidence-<дата>`.

**Зачем.** Чтобы принять ключ самоподписанного узла без участия оператора, его нужно увидеть двумя независимыми путями. SDK даёт для этого две вещи: способ снять ключ по заданному пути и чистую функцию, которая решает, достаточно ли собранных свидетельств. Перебор путей остаётся приложению.

**Сейчас (после S2).** Верификатор умеет ожидание `record`; хранилище знает, какие узлы сверены.

**Сделать.**

1. Функция снятия ключа: на входе путь (цепочка узлов до сверяемого узла либо «напрямую»), сверяемый узел, сроки, коннектор по умолчанию. Она строит туннель до адреса узла существующим кодом цепочек, выполняет TLS-рукопожатие с ожиданием `record` и именем сервера из настроек узла, возвращает `SpkiPin` и закрывает соединение. CONNECT, логин и пароль сверяемого узла не отправляются. Всё под одним общим сроком.
2. Расчёт множества вмешательства для пути: найти последний сверенный HTTPS-узел; множество — он и все узлы после него; если такого нет — все узлы пути. Сверенным считается HTTPS-узел с ручным пином, с записью в хранилище либо со своим CA. Узлы сравниваются существующей функцией `same_upstream`.
3. Типы `Evidence` (наблюдение по каналу с признаком «рабочий путь»; доверенная цепочка) и `VerifyError`.
4. Чистая функция решения: на входе узел, текущая запись (если есть), свидетельства, режим. На выходе новая запись с происхождением `Multipath` либо ошибка. Правило — `design.md`, §3. Функция ничего не читает и не пишет, кроме проверки «сверен ли узел» через переданное хранилище.
5. Варианты `VerifyError`: ключи разошлись (с обоими ключами и путями); свидетельства не независимы; нет сильного свидетельства при смене ключа; единственное свидетельство; оба — рабочий путь; у узла ручной пин.
6. Документация: rustdoc с таблицей примеров из `design.md`, §3; раздел README SDK.

**Не делать.**

- Перебор кандидатов, ярусы, расписание, запись в файл — это приложение (S5b).
- Запись в хранилище из функции решения: её делает вызывающий.

**Ловушки.**

- Запись ключа при рабочем рукопожатии с доверенной цепочкой (S2, п. 8) — частный случай этого же правила: «цепочка плюс рабочий путь». Не заводи второй реализации правила; если меняешь правило, меняй оба места и таблицу в `design.md`.
- В `strict` цепочка к корням Mozilla свидетельством не считается, цепочка к своему CA — считается.
- Сравнение ключей свидетельств — обычное равенство. Свидетельства с разными ключами дают ошибку расхождения даже тогда, когда остальных условий хватает.
- Путь «напрямую» имеет пустое множество вмешательства. Два таких наблюдения — одно свидетельство, а не два.
- Общий срок считается на весь путь: соединение, рукопожатие с каждым узлом пути и рукопожатие со сверяемым узлом.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| Каждая строка таблицы примеров `design.md`, §3 — для первого ключа и для смены ключа | исход по таблице |
| Свидетельства показали разные ключи | ошибка расхождения с обоими ключами; запись не создана |
| Ручной пин у узла | отказ при любых свидетельствах |
| `strict`: цепочка к корням Mozilla и рабочий путь | отказ |
| `strict`: цепочка к своему CA и рабочий путь | принято |
| Канал, где HTTPS-узел есть, но не сверен | считается слабым, в множество входят все узлы |
| Канал с двумя сверенными HTTPS-узлами | множество начинается с последнего |
| Снятие ключа у честного узла напрямую и через цепочку из всех трёх протоколов | ключ равен значению тестовой PKI |
| Снятие ключа через подменяющий узел | возвращён ключ подменяющего узла; его стаб не получил ни байта после рукопожатия |
| Снятие ключа: узел предъявил чужой сертификат без закрытого ключа | ошибка рукопожатия |
| Снятие ключа у молчащего узла | ошибка по общему сроку |
| Снятие ключа | хранилище не изменено |

## S5b. Приложение: объект `verify`, ярусы, сверка

**Зависит от:** S3, S4, S5a. **Крейт:** `resocks5`. **Ветка:** `s5b-verify-<дата>`.

**Зачем.** После S5a несверенный узел стоит на паузе, пока оператор не задаст пин вручную. Эта задача снимает ручной шаг: сервер сам собирает два свидетельства через проверочные узлы и принимает ключ по правилу.

**Сейчас (после S5a).** Узлы на паузе известны; хранилище пинов пишет файл; пробы карантина запускаются из обработки клиентского запроса (`spawn_chain_probes` в `establish_connection/dial.rs`) и при запуске. Живой префикс мостов для пробы строит `healthy_prefix` в `establish_connection/probes.rs`.

**Сделать.**

1. Конфиг: структура `verify` в `config/proxy_list/` с шестью массивами; поле `verify` в `ProxyListConfig`; ключ `tls.verify_via_main`.
2. Проверки конфига (общий код проверок):
   - правила `tls-only`, порта 443/8443 и храповика действуют и на списки `verify`;
   - один `host:port` в основном списке и в `verify` — ошибка;
   - метка `*` в `verify` допустима только в списках `https_*`; такой узел работает как обычный проверочный.
3. Запуск: разобрать списки `verify` тем же кодом, собрать один проверочный ротатор, добавить группу `verify` в файл здоровья. HTTPS-узлы `verify` получают те же настройки TLS и ту же паузу, что основные. Проверочный ротатор не передаётся в обработку клиентов.
4. Новый каталог `server/connect/verify/`:
   - **кандидаты** — ярусы по `design.md`, §8, и порядок внутри яруса. Порядок задаёт устойчивый хэш от пары адресов (сверяемый узел, кандидат): он не должен зависеть от запуска процесса;
   - **сверка одного узла** — сбор свидетельств через функцию снятия ключа, вызов функции решения, запись пина и снятие паузы либо запись в лог;
   - **расписание** — время следующей попытки на узел с ростом паузы вдвое от `quarantine_initial_sec` до `quarantine_max_sec`; не больше одной сверки узла одновременно; общий предел одновременных сверок.
5. Построение путей: путь через верификатор — живой префикс мостов и верификатор; рабочий путь узла — живой префикс мостов старше его ранга либо «напрямую». Код построения префикса использовать общий с пробами.
6. Запуск сверки: при запуске сервера и рядом с `spawn_chain_probes`. Задача сверки отвязана от клиентского запроса, как пробы.
7. Каждое соединение сверки резервирует разрешение пула у каждого узла пути; нет разрешения — кандидат пропускается.
8. Смена ключа: узел на паузе с существующей записью сверяется тем же кодом; правило само требует сильное свидетельство. Старая запись остаётся до успеха.
9. Порядок сверки при запуске: сначала HTTPS-узлы `verify`, затем остальные — чтобы появились сильные каналы.
10. `config check`: для каждого HTTPS-узла — сколько кандидатов в каждом ярусе; отдельным списком узлы, для которых пара свидетельств невозможна.
11. `has_https` учитывает списки `verify`.
12. Документация: `docs/REFERENCE.md`, `docs/ARCHITECTURE.md`.

**Не делать.**

- Выяснять, какой из разошедшихся каналов солгал, и штрафовать его.
- Сверять узел в ходе клиентского запроса: клиент не ждёт сверку.
- Отдельный таймер сверки.
- Использовать проверочные узлы для клиентского трафика при любых условиях, включая «все выходы недоступны».

**Ловушки.**

- Каталог `establish_connection/` заполнен, `probes.rs` — 855 строк: новый код — в `server/connect/verify/`.
- Рандеву-хэш на `RandomState` меняется при каждом запуске; нужен устойчивый хэш (например SHA-256, он уже в зависимостях).
- Узел яруса 1 должен быть жив, сверен и не на паузе в момент выбора; состояние могло измениться после построения списка — проверяй перед использованием.
- В логе пути печатаются как `host:port`, без логина и пароля.
- Проверочный узел, который сам HTTPS и не сверен, не может быть сильным каналом; в `auto` он станет сверенным после первого рукопожатия с доверенной цепочкой.
- Сверка при полностью занятом пуле не должна ни ждать, ни считать узел недоступным.
- Общий срок одной сверки — по образцу `probe_deadline` в `probes.rs`.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| `strict`, HTTPS-узел, сверенный HTTPS-узел в основном списке, `verify` пуст | сверка проходит через ярус 1; пин `multipath`; пауза снята |
| То же при `verify_via_main: false` | ярус 1 не используется; без `verify` узел остаётся на паузе, `ERROR` |
| Ярус 1 пуст, в `verify` есть HTTPS-узел и открытый узел | первым берётся HTTPS-узел |
| Только открытый проверочный узел и рабочий путь | первый ключ принят, в логе `WARN` о слабой паре |
| Только рабочий путь | отказ, `ERROR`, узел на паузе |
| Общий открытый мост, сверенный HTTPS-верификатор за ним | сверка проходит |
| Общий открытый мост, открытый верификатор за ним | отказ: свидетельства не независимы |
| Подменяющий мост на рабочем пути, честный верификатор | расхождение; оба ключа в логе; пин не записан; логин и пароль узла не ушли |
| Смена ключа, доступна только слабая пара | узел на паузе, старая запись в файле |
| Смена ключа, доступен сильный канал | новая запись, старый ключ в истории |
| Повторные неудачи | интервал между попытками растёт вдвое и не превышает предела; после успеха сброшен |
| Два клиентских запроса подряд при несверенном узле | одна сверка, а не две |
| Порядок кандидатов для одного узла в двух запусках процесса | одинаковый |
| Узел из `verify` | ни в одном клиентском запросе не выбран, в том числе когда все выходы недоступны |
| Один `host:port` в основном списке и в `verify`; `*` в открытом списке `verify` | сервер не запускается |
| Пул заполнен | кандидат пропущен, узел не помечен недоступным |
| `config check` | показывает кандидатов по ярусам и узлы без возможной пары |

## S9. CLI `pins`

**Зависит от:** S5b. **Крейт:** `resocks5`. **Ветка:** `s9-cli-pins-<дата>`.

**Зачем.** Оператору нужно видеть, какие ключи приняты и как, уметь забыть ключ (в том числе чтобы снять храповик) и проверить узел вручную с подробным выводом.

**Сейчас.** Группа `tls` в `cli/keys/` (S10); образец работы с файлом под блокировкой — `cli/run_user_command.rs`.

**Сделать.**

1. Группа `Pins { action }` в `cli/command.rs`, ветка в `main.rs`, код в `cli/keys/`.
2. `resocks5 pins list`: таблица — узел, имя сервера, ключ, происхождение, даты первого появления и последней сверки. Узлы с ручным пином берутся из конфига и помечаются `manual`. Записи, которым нет узла в конфиге, помечаются.
3. `resocks5 pins show <host:port>`: запись целиком, включая историю ключей и пути сверки.
4. `resocks5 pins forget <host:port>`: удалить запись из `pins` и адрес из `tls_nodes` под блокировкой. Напечатать, что изменение подействует после перезапуска сервера.
5. `resocks5 pins verify <host:port> [--dry-run]`: загрузить конфиги, собрать ротаторы без запуска листенера, выполнить одну сверку узла кодом S5b. Напечатать каждое свидетельство — путь, ключ, силу — и решение. При успехе записать пин, если не задан `--dry-run`. Ненулевой код при расхождении и при отсутствии пары.

**Не делать.**

- Команды `add`, `import`, `export`: ручной пин задаётся в конфиге, файл переносится копированием.
- Связь с работающим сервером: команда работает с файлами, как `users`.

**Ловушки.**

- `pins verify` не знает, какие узлы сервер считает недоступными. Она читает файл здоровья, если он есть, и иначе считает все узлы живыми; это нужно написать в выводе.
- `pins verify` открывает соединения наружу; остальные команды — нет и не требуют корректного списка прокси.
- Запись файла — по той же схеме «блокировка → чтение → изменение → запись», что у сервера.
- В выводе нет логинов и паролей; пути печатаются как `host:port`.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| `list` на файле с записями разного происхождения | все показаны; запись без узла в конфиге помечена |
| `list` без файла | пустая таблица, нулевой код |
| `show` для отсутствующего узла | ненулевой код |
| `forget` | запись и адрес из `tls_nodes` удалены; остальные не тронуты |
| `forget`, затем запуск с узлом в открытом списке | сервер запускается |
| `forget`, пока другой процесс держит блокировку | ждёт блокировку, чужое изменение не потеряно |
| `verify` с честными стабами | нулевой код; пин записан; в выводе два свидетельства с силой |
| `verify --dry-run` | файл не изменён |
| `verify` с подменяющим узлом | ненулевой код; оба ключа в выводе; файл не изменён |
| `verify` без возможной пары | ненулевой код, причина названа |
| Вывод всех команд | логинов и паролей нет |

## S7. Сквозные сценарии, документация, CHANGELOG

**Зависит от:** все задачи. **Крейты:** оба. **Ветка:** `s7-finish-<дата>`.

**Зачем.** Каждая задача проверяла свою часть. Здесь проверяется, что части работают вместе на собранном сервере, и приводится в порядок документация для пользователей и потребителей SDK.

**Сделать.**

1. Сквозные тесты по таблице `testing.md`, §6, на сервере со стабами узлов. Рекомендуемое место — новый файл тестов в `server/bootstrap/`.
2. Проверить, что тесты новых модулей попадают в нужные задачи CI: при необходимости добавить имена в задачу `release-behavior` и обновить классификатор путей `.github/scripts/changed-areas.sh` вместе с его тестом.
3. Документация для пользователя:
   - `docs/REFERENCE.md`: секции `tls`, `listen_tls`, объект `verify`, флаг `;plain_ok`, файлы состояния, команды `config check`, `tls`, `pins`, раздел «что делать, если узел не сверен»;
   - `README.md` репозитория: краткое описание возможностей;
   - `docs/ARCHITECTURE.md`: состояния узла, сверка, место нового кода;
   - `SECURITY.md`: модель угроз из `design.md`, §1, и известные ограничения из §13.
4. Документация SDK: `crates/resocks5-net/README.md` — настройки TLS узла, пины, правило свидетельств, пауза в ротаторе; пример в блоке `text`.
5. `CHANGELOG.md`, раздел `[Unreleased]`:
   - Added: всё новое;
   - Changed: неизвестный ключ конфига останавливает запуск; открытый узел на 443/8443 требует `;plain_ok`; HTTPS-узлы пробуются по TLS;
   - для потребителей SDK: новые варианты `ConnectError`, новое поле `ProxyConfig.tls`, `pick_order` может вернуть пустой список при паузе всех узлов.
6. Обновить этот каталог: статус «сделано», расхождения дизайна с реализацией внесены в `design.md`.

**Не делать.**

- Поднимать версию, ставить тег, публиковать. Это делает пользователь отдельной командой; ожидаемая версия — 0.6.0.

**Ловушки.**

- `docs/REFERENCE.md` встроен в бинарник; тесты `print_config_docs::` сверяют его с выводом.
- В `docs/` нельзя добавлять новые записи: каталог заполнен.
- Перед тегом `main` должен быть зелёным; релиз идёт через `.github/workflows/release.yml` по тегу `v*`.
- Потребителю SDK `ptrs-gesher` стоит сообщить о новых вариантах ошибок до релиза.

**Приёмка.**

- Все сценарии `testing.md`, §6, зелёные в CI на трёх ОС.
- `cargo doc` без предупреждений в обычной и «тощей» сборке.
