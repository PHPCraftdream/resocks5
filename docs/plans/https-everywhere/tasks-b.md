# Задачи: веха B (пины)

Перед началом прочитай `README.md`, `design.md` (§2, §4, §5, §7, §11, §12) и `codebase.md`.

Порядок: S2 → S4 → S5a. После вехи B работают режим `auto` с записью ключей, ручные пины, самоподписанные узлы и узлы по IP. Сверки по каналам ещё нет: несверенный узел остаётся на паузе, пока оператор не задаст ручной пин.

## S2. SDK: пины и единый верификатор

**Зависит от:** S1, S11. **Крейт:** `resocks5-net`. **Ветка:** `s2-pins-<дата>`.

**Зачем.** Сертификат узла сегодня проверяется только по цепочке к корням. Этого мало в двух случаях: у узла самоподписанный сертификат либо цепочку удалось подделать. Пин привязывает узел к конкретному ключу. Эта задача вводит хранилище ключей, верификатор с ожиданием и ошибки, по которым приложение отличает «узел не сверен» от «ключ сменился».

**Сейчас (после S1).** У узла есть `TlsOptions` с именем сервера и корнями; клиент TLS строится один раз.

**Сделать.**

1. `connect/tls/trust/`: `PinKey`, `PinOrigin`, `PinRecord`, трейт `PinStore`, `MemoryPinStore`, `PinningMode`.
2. `TlsOptions`: построители `manual_pin` и `pin_store(store, mode)`.
3. Расчёт ожидания по таблице `design.md`, §2: по настройкам узла, режиму и текущей записи хранилища получить части `chain` и `pin`.
4. Верификатор, реализующий `ServerCertVerifier`:
   - проверка сертификата: при `record` принять; иначе принять, если сошлась цепочка или SPKI равен пину; иначе вернуть ошибку, в которую вложены причина и снятый ключ (`CertificateError::Other`);
   - проверка подписи TLS 1.2 и TLS 1.3 — всегда штатными функциями `rustls` с алгоритмами провайдера;
   - список поддерживаемых схем подписи — из провайдера.
5. Кэш клиента TLS по текущему пину: пин в хранилище изменился или исчез — клиент строится заново. Старый клиент вместе со своим кэшем сессий отбрасывается.
6. Предпроверка узла (`preflight` из S11) под `cfg(feature = "tls")`: HTTPS-узел с `TlsOptions`, у которого ожидание пусто, отказывает `Unverified` до открытия сокета.
7. Разбор ошибки рукопожатия в `https_hop` и `https_on_stream`: достать вложенную причину и вернуть `PinMismatch` (пин был и не совпал) либо `Unverified` (пина нет, цепочка не сошлась). Остальные ошибки TLS — как сейчас.
8. Запись ключа после успешного рабочего рукопожатия в тех же двух местах: ключа в хранилище нет — записать с происхождением `Ca` или `WebPki`; ключ другой — записать новый, прежний добавить в историю (не больше 8). Узлы с ручным пином в хранилище не пишутся.
9. `ConnectError::{Unverified, PinMismatch}`: текст, три функции классификации, тесты. Свойства — `design.md`, §11.
10. Документация: rustdoc, раздел в README SDK.

**Не делать.**

- Функцию снятия ключа и правило свидетельств — это S3. Режим `record` в верификаторе делается здесь, но наружу не выставляется.
- Писать в хранилище из верификатора: в этот момент подпись ещё не проверена.
- Обновлять запись при каждом рукопожатии с тем же ключом: запись меняется только при появлении и смене ключа.

**Ловушки.**

- При возобновлении сессии `rustls` не вызывает проверку сертификата. Безопасность держится на кэше по пину (п. 5), а не на верификаторе. Это проверяется отдельным тестом.
- Трейт `PinStore` синхронный и вызывается на пути соединения: реализация обязана отвечать из памяти. Ввод-вывод — за пределами вызова.
- `ServerCertVerifier` требует `Debug`; в отладочном выводе не должно быть ничего, кроме пина и имени.
- Корни Mozilla для режима `auto` берутся из существующей функции в `upstream_tls.rs`, второй набор корней не заводится.
- Ошибка `tokio-rustls` — это `io::Error`, внутри которой лежит `rustls::Error`. Проверь тестом, что вложенная причина извлекается, а не теряется.
- Узел без `TlsOptions` ведёт себя как раньше: переданный коннектор, цепочка к его корням, без записи ключей.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| `strict`, пин в хранилище равен ключу узла, сертификат самоподписанный | рукопожатие проходит |
| `strict`, пин не равен ключу | `PinMismatch` с обоими ключами |
| `strict`, пина нет | `Unverified`; считающий листенер: 0 соединений |
| `auto`, пина нет, цепочка к корням из настроек сходится | проходит; в хранилище появилась запись с верным ключом и происхождением |
| `auto`, пина нет, сертификат самоподписанный | `Unverified` со снятым ключом; запись не появилась |
| `auto`, пин есть, ключ сменился, цепочка сходится | проходит; запись заменена, старый ключ в истории |
| `auto`, пин есть, ключ сменился, цепочка не сходится | `PinMismatch`; запись не изменилась |
| Ручной пин, ключ совпал | проходит; хранилище не тронуто |
| Ручной пин, ключ не совпал, цепочка сходится | `PinMismatch`: ручной пин строже цепочки |
| Верный сертификат, неверная подпись рукопожатия (во всех трёх видах ожидания, включая `record`) | рукопожатие сорвано |
| Пин в хранилище заменён на чужой после успешного соединения; узел тот же | следующее соединение даёт `PinMismatch`, сессия не возобновлена |
| История ключей | не длиннее 8 |
| Пин на первом, среднем и последнем узле цепочки; путь с пулом и без | одинаковый результат |
| Классификация: `Unverified` не засчитывается узлу как отказ; `PinMismatch` — жёсткий отказ | по таблице `design.md`, §11 |
| Сборка без `tls` | новых типов нет, `clippy` чист |

## S4. SDK: пауза узла, TLS-проба, фрагментация ClientHello

**Зависит от:** S2. **Крейт:** `resocks5-net`. **Ветка:** три ветки и три PR, по одной на часть.

**Зачем.** Три независимых механизма, нужных приложению в S5a:

- несверенный узел не должен выдаваться ротатором, чтобы клиентский запрос не тратил на него попытку;
- проба HTTPS-узла после карантина должна проверять TLS, а не только TCP;
- наш ClientHello к HTTPS-узлу должен фрагментироваться так же, как ClientHello клиента.

### Часть 1. Пауза в ротаторе

**Сейчас.** Выбор узлов живёт в `Ratings` (`session/rating/mod.rs`): `pick`, `pick_order`, ленивый порядок. Узлы в карантине пропускаются, **но если здоровых нет, возвращаются все**. `ProxyRotator::get_next` возвращает узел, а не `Option`.

**Сделать.**

1. Перенести файлы тестов `rotator/construction_tests.rs`, `probe_tests.rs`, `quarantine_tests.rs`, `tests.rs` в подкаталог `rotator/tests/`. Отдельный коммит без изменения содержимого.
2. Признак паузы на каждый узел в `Ratings`. Узел на паузе исключается из выбора всегда, в том числе в ветке «здоровых нет».
3. `ProxyRotator::hold`, `release`, `is_held` — по `ProxyConfig`, как существующие `record_failure` и `is_quarantined`. Возвращают, изменилось ли состояние.
4. Узел на паузе не выдаётся в `take_probes` и `take_probe_claims`.
5. `health()` и `restore_health()` паузу не читают и не меняют.
6. `get_next`: пропускает узлы на паузе; если на паузе все — возвращает узел на паузе. Это записывается в документации метода: подпись без `Option` менять нельзя, а соединение с таким узлом всё равно откажет в SDK.

**Ловушки.**

- `pick_order` и `pick_iter` теперь могут вернуть пустой результат. Найди всех вызывающих в SDK (`session/chain/mod.rs`, `connect/proxy_connect/hedged.rs`) и убедись, что пустой слой обрабатывается, а не приводит к панике или делению на ноль.
- `rating/mod.rs` — 825 строк, каталог `rating/` заполнен: код паузы клади в существующие файлы с запасом (`quarantine.rs`, `health.rs`).
- Код живёт под features `rating` и `rotator`, не под `tls`.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| Узел на паузе, остальные здоровы | `pick_order`, `pick_iter`, `pick` его не выдают |
| На паузе все узлы | `pick_order` и `pick_iter` пусты |
| На паузе один, остальные в карантине | выдаются узлы из карантина, узел на паузе — нет |
| Карантин выключен политикой | пауза работает |
| `restore_health` с записью «жив» для узла на паузе | пауза сохраняется |
| `release` | узел снова выдаётся |
| `ChainPlan`, где слой мостов целиком на паузе | план пуст, без паники |
| Узел на паузе с истёкшим карантином | в `take_probes` не попадает |

### Часть 2. TLS-проба

**Сейчас.** `probe_due_with` и `probe_all_with` (`session/rotator/probe.rs`) открывают TCP и по результату возвращают узел в работу либо продлевают карантин.

**Сделать.**

1. `probe_due_tls_with` и `probe_all_tls_with`: для узла с протоколом `Https` после TCP выполняется TLS-рукопожатие с тем же ожиданием, что у рабочего соединения. Для остальных протоколов поведение прежнее. Параметры: срок соединения, срок рукопожатия, коннектор по умолчанию, резерв разрешения.
2. Исход: рукопожатие прошло — `Recovered`; ошибка TLS или срок — `StillDown` с причиной.
3. Существующие `probe_due*` и `probe_all*` не меняются.

**Ловушки.**

- Проба не отправляет CONNECT, логин и пароль.
- Проба через цепочку (узел за мостом) остаётся в приложении: там рукопожатие уже проходит через `hop`.
- Заявка на пробу (`UpstreamProbeClaim`) привязывает исход к поколению слота: используй тот же механизм, чтобы устаревший исход не перезаписал состояние.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| HTTPS-узел в карантине, сертификат верный | `Recovered` |
| HTTPS-узел, TCP открыт, сертификат чужой | `StillDown`, причина называет TLS |
| HTTPS-узел, TCP открыт, рукопожатие молчит | `StillDown` по сроку рукопожатия |
| SOCKS5-узел | поведение как у `probe_due` |
| Стаб HTTPS-узла | после рукопожатия не получил ни байта |

### Часть 3. Фрагментация нашего ClientHello

Наименее срочная часть: веху B можно выпустить без неё.

**Сейчас.** `send_possibly_fragmented` (`connect/tls/tls_fragment/mod.rs`) отправляет готовый буфер с ClientHello клиента частями. Наш собственный ClientHello пишет `tokio-rustls` напрямую в поток.

**Сделать.**

1. В `connect/tls/tls_fragment/`: обёртка потока. Первую запись, распознанную как ClientHello (`classify_client_hello`), она отправляет частями по `FragmentSpec`; после этого пропускает данные без изменений.
2. Реализация `AsyncRead`, `AsyncWrite` и `AsyncReadWrite` для обёртки.
3. `TlsOptions::fragment_hello(spec)`; в `https_hop` поток оборачивается перед рукопожатием.
4. Путь с пулом: `connect_https_proxy` возвращает конкретный тип потока, менять его нельзя. В `connect_proxy_on` узел с включённой фрагментацией обрабатывается через путь с обобщённым потоком (как в цепочках) и возвращается вариантом `AnyUpstream::Gate`. В документации `connect_https_proxy` указать, что фрагментация там не применяется.

**Ловушки.**

- Задержка между частями внутри `poll_write` требует собственного автомата состояний с таймером; `async fn` тут неприменима.
- Обёртка ставится над потоком, который уже обёрнут в `ProgressReportingWriter`: учёт прогресса записи должен остаться верным.
- Проверь, что код приложения не различает `AnyUpstream::Tls` и `AnyUpstream::Gate` там, где это меняет поведение.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| Фрагментация включена | стаб получает ClientHello несколькими чтениями; имя сервера не помещается в первое |
| Фрагментация включена | рукопожатие и CONNECT проходят, данные туннеля не изменены |
| Фрагментация выключена | поток не оборачивается, поведение прежнее |
| Медленный получатель | запись не зависает и ограничена сроком рукопожатия |
| Путь с пулом и без | одинаковое поведение на проводе |

## S5a. Приложение: файл пинов, несверенный узел, храповик

**Зависит от:** S2, S4 (части 1 и 2). **Крейт:** `resocks5`. **Ветка:** `s5a-pins-file-<дата>`.

**Зачем.** SDK умеет проверять пин, но ключи нужно хранить между запусками, несверенные узлы нужно убирать из выбора, а оператор должен иметь способ задать ключ вручную. Эта задача подключает механизмы S2 и S4 к приложению.

**Сейчас (после S12).** Есть секция `tls` с `transport` и `nodes{sni, ca_file}`; HTTPS-узлы получают `tls_only` и `TlsOptions` при запуске. Образец файла состояния — `server/health/mod.rs`: атомарная запись под `UsersFileLock`, запись вне асинхронного пути, сохранение при остановке.

**Сделать.**

1. `server/health/pins.rs`: модель файла (`version`, `tls_nodes`, `pins`), терпимое чтение, запись по схеме «блокировка → чтение → применение изменения → атомарная запись». Константа пути рядом с `HEALTH_PATH`.
2. Файловое хранилище, реализующее `PinStore`: чтение из памяти; `put` меняет память и ставит запись файла в очередь вне пути соединения. При смене ключа — `WARN` с адресом узла и обоими ключами, при первой записи — строка жизненного цикла. При остановке сервера очередь дописывается.
3. Конфиг: `tls.pinning` (`auto` по умолчанию, `strict`), `tls.nodes{…}.pin`. Проверки: значение пина разбирается; `pin` и `ca_file` не заданы одновременно.
4. Запуск: каждый HTTPS-узел основных списков получает `TlsOptions` с хранилищем и режимом, ручным пином, а при включённой секции `tls_fragment` — с фрагментацией.
5. Запуск: `tls_nodes` пополняется адресами всех узлов из списков `https_*`.
6. Храповик: проверка в общем коде проверок (S12) — адрес из `tls_nodes` стоит в открытом списке. Файл пинов читается до проверок; `config check` читает его без записи.
7. Пауза при запуске: HTTPS-узел в состоянии «не сверен» (`design.md`, §5) ставится на паузу в своём ротаторе. В `auto` узел без пина на паузу не ставится.
8. Пауза в работе: соединение вернуло `Unverified` или `PinMismatch` — узел, названный в ошибке, ставится на паузу; попытка не засчитывается как отказ узла и не ведёт в карантин. В лог — одна строка на переход, а не на каждую попытку.
9. Пробы: `spawn_due_probes` и проверка при запуске переходят на `probe_due_tls_with` и `probe_all_tls_with`.
10. `config check`: колонки состояния пина и происхождения; список узлов, которые не смогут начать работу без ручного пина.
11. Нет файла пинов при наличии HTTPS-узлов — `WARN` при запуске.
12. Документация: `docs/REFERENCE.md`, комментарий-шапка `config/mod.rs` со списком файлов.

**Не делать.**

- Объект `verify`, сверку по каналам, автоматическое снятие паузы — это S5b. В этой вехе узел уходит с паузы только после перезапуска с ручным пином.
- Перечитывать файл пинов в работающем сервере.
- Писать ручной пин в файл.
- Сохранять паузу в файл здоровья.

**Ловушки.**

- Файл здоровья включается только при `health_save_sec > 0` и `quarantine_threshold > 0`. Файл пинов от этих настроек не зависит.
- Узел, названный в ошибке, может принадлежать ротатору моста, а не выхода. Ищи узел по адресу из ошибки во всех ротаторах цепочки, не выводи его из стадии ошибки.
- Все узлы на паузе — у клиента ошибка «нет маршрута». В логе это должно читаться как «все HTTPS-узлы не сверены», а не как сетевой сбой.
- `health/mod.rs` — 844 строки: новый код только в `pins.rs`.
- Запись файла на Windows: используй тот же код, что `users` и `health`, включая блокировку.
- Формат ключа карты `tls.nodes` — результат S12.

**Приёмка.**

| Тест | Ожидание |
|---|---|
| Запись и чтение файла | круговой тест; паролей в файле нет |
| Файл с неизвестным полем и большим `version` | читается |
| Повреждённый файл | HTTPS-узлы без ручного пина на паузе, сервер работает, `ERROR` в логе; файл не перезаписан |
| Параллельная запись сервером и изменение файла другим процессом под блокировкой | оба изменения сохранены |
| Сбой записи | прежний файл цел |
| Старый конфиг, HTTPS-узел с доверенной цепочкой, файла нет, `auto` | клиент обслужен; запись появилась; `WARN` об отсутствии файла |
| `strict`, HTTPS-узел без пина | на паузе; клиент его не получает; стаб узла: 0 соединений |
| То же при `quarantine_threshold = 0` | на паузе |
| Восстановление файла здоровья с записью «жив» для несверенного узла | узел остаётся на паузе |
| Ручной пин, ключ совпал | узел работает; в `pins` файла записи нет |
| Ручной пин не разбирается; `pin` вместе с `ca_file` | сервер не запускается |
| Узел работал, ключ сменился, цепочка не сходится | узел на паузе, попытка не привела в карантин, одна строка в логе |
| `auto`, самоподписанный узел | первая попытка даёт `Unverified`, узел на паузе, клиент обслужен другим узлом |
| Узел из `https_v4` перенесён в `http_v4` | сервер не запускается, сообщение называет узел и `pins forget` |
| Узел удалён из конфига совсем | запускается |
| Проба HTTPS-узла с чужим сертификатом | узел остаётся в карантине |
| `config check` | показывает состояние пина; файл пинов не изменён |
| Остановка сервера | очередь записи дописана |
