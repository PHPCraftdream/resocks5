# Тесты

Общие правила и инфраструктура. Сценарии приёмки каждой задачи — в её карточке.

## 1. Принципы

- Тесты запускает только CI. Локально — `cargo check`, `cargo clippy`, `cargo fmt`.
- Сеть — только loopback. Обращений во внешнюю сеть в тестах нет.
- Сроки проверяются на остановленных часах (`#[tokio::test(start_paused = true)]`) поверх потоков в памяти. Настоящий сокет нужен только там, где проверяется поведение сокета.
- Каждый тест проверяет наблюдаемое поведение: байты на проводе, тип ошибки, состояние файла, код возврата. Сравнение текста сообщения допустимо только для сообщений, которые читает оператор.
- Ошибки сравниваются через `matches!` по варианту, а не по строке.
- Имя теста — утверждение о поведении, как в существующих тестах: `a_tighter_handshake_bound_still_reports_the_stage`.
- Тест, написанный вместе с исправлением, должен падать без исправления. Проверь это рассуждением по коду, раз запускать локально нельзя, и напиши в описании PR, какая строка делает тест красным.
- Секретов в тестах нет: логины и пароли вида `user`/`pass`, ключи создаются в самом тесте.
- Нестабильный тест чинится сразу и до причины.

## 2. Тестовая PKI (создаётся в S0)

Нужны сертификаты с разными ключами: честный узел, подменяющий узел, свой CA, самоподписанный, с IP SAN и без. Статических фикстур для этого мало, поэтому используется `rcgen` на `ring`.

**SDK.** Модуль под `#[cfg(test)]` в `connect/tls/trust/`:

| Функция | Что даёт |
|---|---|
| `test_ca()` | самоподписанный CA и его ключ |
| `leaf(ca, names)` | лист, подписанный CA, с именами DNS и IP |
| `self_signed(names)` | самоподписанный лист |
| `acceptor(cert, key)` | `TlsAcceptor` для стаба |
| `roots(ca)` | `RootCertStore` с этим CA |
| `spki_pin(cert)` | ожидаемый пин, посчитанный независимо от боевого кода |

`spki_pin` в тестах не должен вызывать ту же функцию, которую проверяет: иначе тест сравнивает код с самим собой. Считай хэш от SPKI, который отдаёт `rcgen` (ключевая пара знает свой открытый ключ в DER).

**Приложение.** Генерация самоподписанной пары — боевой код (нужен команде `tls init`), поэтому `rcgen` в приложении — обычная зависимость. Тесты приложения вызывают этот же код и `rcgen` напрямую.

Существующие статические сертификаты (`CA_DER_B64` в SDK, `STUB_CERT_PEM` в приложении) остаются: на них стоят действующие тесты.

## 3. Стабы

Строятся на существующих стабах приложения (`server/connect/establish_connection/tests/matrix.rs`) и SDK (`connect/dial/tests.rs`, `connect/tls/upstream_tls.rs`).

| Стаб | Поведение | Для чего |
|---|---|---|
| Считающий листенер | принимает TCP, считает соединения и полученные байты, ничего не отвечает | доказать «сокет не открыт» и «ни байта не ушло» |
| Честный узел | говорит свой протокол (SOCKS5, HTTP, HTTPS с заданным сертификатом), пробрасывает к цели | каналы сверки, матрица цепочек |
| Подменяющий узел | на CONNECT к HTTPS-узлу не пробрасывает поток, а сам завершает TLS своим ключом и записывает, что получил после рукопожатия | подмена мостом; проверка, что логин и пароль не ушли |
| Узел с заменяемым ключом | HTTPS-узел, которому тест меняет сертификат между соединениями | смена ключа, возобновление сессий |
| Молчащий узел | принимает TCP и не отвечает | сроки |
| Клиент TLS | `rustls`-клиент с заданными корнями | входящий TLS |

Каждый стаб закрывается явно в конце теста или привязан к задаче, которая отменяется при выходе из теста: висящих задач быть не должно.

## 4. Обязательные утверждения

Эти проверки повторяются во многих задачах; формулировка должна быть одинаковой.

| Утверждение | Как проверить |
|---|---|
| Отказ до сокета | считающий листенер на адресе узла: 0 соединений |
| Ни байта открытым текстом | считающий листенер: 0 байт; для пути с пулом — ещё и разрешение пула не занято |
| Логин и пароль не ушли подменяющему узлу | подменяющий узел записал 0 байт после рукопожатия либо рукопожатие не завершилось |
| Пин не записан | хранилище пусто либо не изменилось |
| Узел не получил клиента | `pick_order` и `pick_iter` его не содержат; стаб узла насчитал 0 соединений за время теста |
| Файл цел после сбоя записи | повторное чтение даёт прежнее содержимое |
| Секрет не напечатан | вывод команды и текст ошибки не содержат пароля и закрытого ключа |

## 5. Комбинации features

Новой feature нет, матрица `net-features` не меняется. Весь новый код SDK — под `tls`. Это значит:

- без `tls` ничего нового не компилируется, а HTTPS-узел по-прежнему даёт `TlsFeatureMissing` до сокета — на это есть тест;
- `clippy` чист в четырёх комбинациях: без features, только `pool`, только `tls`, все;
- пауза в ротаторе (`hold`) живёт под `rotator`, а не под `tls`;
- фикстура `tests/feature_unification` продолжает собираться: «тощий» потребитель без `tls` не должен увидеть новых обязательных аргументов.

## 6. Сквозные сценарии (задача S7)

Запускаются на собранном сервере со стабами узлов. Каждый сценарий — отдельный тест.

| № | Сценарий | Ожидание |
|---|---|---|
| 1 | Обновление: старый конфиг с HTTPS-узлом с публичной цепочкой, файла пинов нет | клиент обслужен, пин записан с `origin: webpki`, в логе `WARN` об отсутствии файла |
| 2 | `strict`, HTTPS-узел, проверочные узлы есть | до сверки клиент узел не получает; после сверки получает; пин `multipath` |
| 3 | `strict`, проверочных узлов нет | узел не используется, `ERROR` в логе, сервер работает на остальных узлах |
| 4 | Подменяющий мост перед HTTPS-узлом, честный проверочный узел | ключи разошлись, пин не записан, логин и пароль узла не ушли |
| 5 | Общий локальный мост, сверенный HTTPS-верификатор | сверка проходит |
| 6 | Смена ключа у узла с пином `multipath`, доступна только слабая пара | узел остаётся на паузе, старый пин в файле |
| 7 | Смена ключа, доступен сильный канал | новый пин, старый в `history`, `WARN` |
| 8 | Узел перенесён из `https_v4` в `http_v4`, пин в файле есть | сервер не запускается; после `pins forget` запускается |
| 9 | `tls-only` и SOCKS5-узел в списке | сервер не запускается, сообщение называет список и номер строки |
| 10 | Опечатка в ключе секции `tls` | сервер не запускается, сообщение называет ключ |
| 11 | Клиент подключается к порту `listen_tls` по TLS и делает CONNECT | туннель работает |
| 12 | Клиент шлёт открытый CONNECT на порт `listen_tls` | соединение закрыто без ответа |
| 13 | Карантин выключен (`quarantine_threshold = 0`), несверенный узел | клиент узел не получает |
| 14 | `resocks5 config check` на конфиге из сценариев 9 и 10 | ненулевой код, те же сообщения, что при запуске |
